# Event ordering

Every run emits a stream of events, and every event lands in the `run_events` table with two integer columns that place it in the timeline: `sequence_index` and `iteration_index`. Those two numbers are how dendrux gives you a single ordered log per run, and how an SSE client can reconnect after a network blip without missing or double-processing an event.

## The two ordering columns

| Column | Scope | What it means |
| --- | --- | --- |
| `sequence_index` | Run | A global per-run counter. Starts at 0 on `run.started`, increments by 1 for every event the run writes, and never resets, not even across pause and resume (on a database where every writer is on 0.5.0 or later; during a mixed 0.4.1 and 0.5 fleet one duplicate index is possible, see below). |
| `iteration_index` | Loop turn | The LLM iteration the event belongs to. Loop-level events (`run.started`, `run.paused`, `run.resumed`, `run.completed`) record iteration 0. Events produced inside an LLM turn (like `llm.completed`, `tool.completed`, `approval.requested`) record the turn number they came from. |

The only guarantee readers need is the first one: **within a run, `sequence_index` is monotonic, and strictly so once every writer is on 0.5.0 or later**. Order events by it and you get the exact order the runtime observed them.

**How the number is allocated.** Since 0.5.0 the database assigns it in the same statement that inserts the event (`INSERT ... SELECT COALESCE(MAX(sequence_index), -1) + 1`), and the store returns it. There is no counter in your process, so several workers writing to one run (a resume in another process, for example) cannot interleave to reuse a number. A custom `StateStore` must do the same; see [Upgrading to 0.5.0](/docs/upgrading-to-0.5.0#10-custom-statestore-changes).

A unique index on `(agent_run_id, sequence_index)` arrives in 0.5.1, after every worker is on 0.5.0 or later. Until then, a fleet that mixes 0.4.1 and 0.5 workers can in rare races write one duplicate index, and an SSE cursor can miss that one event. That window closes with the 0.5.1 index.

## A real event timeline

The timeline below is the `run_events` log from the quickstart run, dumped from `quickstart.db`. Captured on Dendrux 0.5.0 with claude-haiku-4-5. The run paused for approval after iteration 1, then resumed and finished in iteration 2.

| Sequence | Event | Iteration | Note |
| --- | --- | --- | --- |
| 0 | `run.started` | 0 | Loop-level. Agent name and system prompt recorded. |
| 1 | `tools.declared` | 0 | The tools declared in code, recorded once per run segment (0.5.0). |
| 2 | `llm.completed` | 1 | First LLM turn. 594 input tokens, 55 output, has_tool_calls=true. |
| 3 | `approval.requested` | 1 | refund was declared require_approval. Correlated by call_id. |
| 4 | `run.paused` | 1 | Runtime persists waiting_approval and exits. Client reconnect point. |
| 5 | `run.resumed` | 0 | submit_approval loads the run and re-enters the loop. |
| 6 | `tools.declared` | 0 | Recorded again for the resumed segment (0.5.0). |
| 7 | `tool.completed` | 1 | refund actually executes now. Same iteration as the approval request. |
| 8 | `approval.decided` | 1 | Governance row records who decided and how. |
| 9 | `llm.completed` | 2 | Second LLM turn (668 input, 28 output). No tool calls this time. |
| 10 | `run.completed` | 0 | Terminal event. status=success. |

Notice that `sequence_index` runs straight through pause and resume. `seq=4` and `seq=5` are written in two separate processes (the starter and the resumer), but they are adjacent in the log. On resume the runtime reads `max(sequence_index)` from the DB and continues counting from there, so there is no gap and no collision once every writer is on 0.5.0 or later.

`iteration_index` behaves differently: it jumps between 0, 1, and 2 depending on whether the event is loop-level or turn-scoped. That is by design. Loop-level events belong to no single LLM turn.

## What a client sees on the wire

Your application can expose this log through `RunStore.follow(run_id, tenant_id=...)`.
Each stored event has a monotonic `sequence_index`; an SSE route can use it as the
frame ID and accept the last received ID on reconnect. Your transport owns frame
serialization, header auth, cursor validation, 204/503 handling, send deadlines and
cleanup. See [Build your own read routes](/docs/recipes/build-your-own-read-routes).

## Reconnect without loss or duplicates

Your application chooses its cursor policy. One possible reconnect order is:

1. `Last-Event-ID` header from the reconnect (precedence, with a fallback if the header is malformed).
2. `?after=N` query string.
3. `None`, which means replay from the start of the log.

The resolved cursor is passed into `RunStore.get_events(run_id, after_sequence_index=cursor)`, which emits a SQL `WHERE sequence_index > cursor` and orders by `sequence_index`. The strict `>` is the critical piece: the event the client already saw is excluded, and every event after it is included.

A client that last saw `seq=4` and reconnects gets the rest of the run, no duplicates and no gaps (on a database where every writer is on 0.5.0 or later; see the mixed-fleet note above):

```python

# [5, 6, 7, 8, 9, 10]
```

A complete, self-contained version you can run. A short run produces a four-event log (`run.started`, `tools.declared`, `llm.completed`, `run.completed`); reading it back with `after_sequence_index` excludes the event the client already saw:

```python
import asyncio

from dendrux import Agent
from dendrux.llm.anthropic import AnthropicProvider
from dendrux.store import RunStore


async def main() -> None:
    url = "sqlite+aiosqlite:///events.db"

    async with Agent(
        name="QA",
        provider=AnthropicProvider(model="claude-haiku-4-5"),
        prompt="Answer in one short sentence.",
        database_url=url,
        strict_tenancy=False,  # single-tenant example; see Multi-tenancy
    ) as agent:
        result = await agent.run("What is the capital of France?")

    store = RunStore.from_database_url(url)
    async with store:
        print([e.sequence_index for e in await store.get_events(result.run_id)])
        # [0, 1, 2, 3]

        # A client that already saw seq=0 reconnects: strict > cursor, no replay of seq 0.
        resumed = await store.get_events(result.run_id, after_sequence_index=0)
        print([e.sequence_index for e in resumed])
        # [1, 2, 3]


asyncio.run(main())
```

## Why a DB-backed cursor instead of an in-memory queue

A typical event-bus design broadcasts new events through an in-process pub/sub queue. It is fast, but it does not survive process restarts, it does not work across multiple web instances, and it cannot replay events the client missed while offline.

Dendrux keeps the log in the `run_events` table and polls it. The tradeoff is a few extra SQL queries per second per watched run while a client is streaming, in exchange for three real properties:

1. **Replay is free.** A client that reconnects after any amount of downtime gets everything it missed from the exact same code path that served the first read.
2. **No message bus.** Clients watching the same run in one process share one polling query that fans out in memory, and nothing is shared between processes, so adding a second server instance needs no shared state.
3. **Events are durable.** If the runner crashes mid-iteration, events written before the crash are still visible to readers. Nothing lives only in memory.

`RunStore.follow` yields heartbeats when a run is quiet so your route can send a periodic keepalive and keep reverse proxies from closing idle connections. Dendrux ships no SSE endpoint and no wire framing of its own: your route chooses the frames, and a browser client that must send an authorization header reads them with `fetch` rather than the native `EventSource`. See [Build your own read routes](/docs/recipes/build-your-own-read-routes).
