# Governance

"Governance" in dendrux is the name for everything that happens around the model, not inside it. When a PII pattern is detected in a message, when an approval is requested, when a tool is denied by policy, when a spend budget trips a threshold: all of it is governance. Four different concerns, one unified pipeline.

The pipeline is a plain event stream. Every governance concern emits a typed event. Every typed event flows through the recorder (writes to the DB for durable audit) and the notifier (broadcasts live to any attached observer). Readers consume the same stream that was written. There is no separate "audit subsystem" sitting off to the side.

This page is the map. Each concern has its own page for the details.

## The four concerns

| Concern | What it does | Reference |
| --- | --- | --- |
| [Guardrails](/docs/architecture/guardrails) | Scan every message before and after the LLM. Built-in detectors for [PII](/docs/architecture/pii-redaction), secrets, and [prompt injection](/docs/recipes/prompt-injection-patterns), plus custom regex patterns. Redact, block, or warn. | `dendrux.guardrails` |
| [Approval](/docs/architecture/approval) | Pause the run before a gated tool executes. A human decides approve or deny, for the whole batch or call by call. | `require_approval=[...]` |
| [Access control](/docs/architecture/access-control) | Policy gate on tool calls, skill invocations, and MCP connections. Denies at the boundary before state changes. A [`before_tool` hook](/docs/architecture/tool-policy) adds argument-aware decisions (deny, require approval, substitute a result). | `deny=[...]`, `deny_skills=[...]`, `before_tool=...` |
| [Budget](/docs/architecture/budget) | Track per-run token and dollar spend, including delegated child runs. Raise threshold events at configurable ratios and, if you choose, pause or cancel the run at the cap. | `budget=Budget(...)` |

Guardrails, approval, and access control are independent. You can use any one, any two, any three, or all four on the same run. The runtime applies them in a fixed order (incoming guardrail → static deny → `before_tool` hook → approval → tool execute → outgoing guardrail), but each layer does not know or care about the others. Their only coupling is the shared event log.

## The event types

Governance events are distinct from lifecycle events (`run.started`, `run.paused`, `llm.completed`, `tool.completed`, `run.completed`). Lifecycle events describe what the runtime did. Governance events describe what a governance layer decided.

The six image events (`image.*` and `guardrail.image_unscanned`) record what happened to images the runtime sent, dropped, replaced or could not scan. Their payloads carry ids, counts and verdicts, never image bytes. See [Images](/docs/recipes/images#what-is-recorded).

`guardrail.detected` carries direction, finding count, and entity-type names. `guardrail.blocked` carries direction, an error string, the finding kinds with their counts and a location; since 0.5.0 it never contains the matched text. `guardrail.restore_skipped` records, as counts only, that [PII restore](/docs/architecture/pii-restore) kept a placeholder out of a tool that is not allowlisted. `governance.changed` is described [below](#detecting-changed-governance-on-resume). At the start of every run segment Dendrux also records `tools.declared` (`{"local_tool_names": [...]}`, the tools declared in code), which redacted readers use to prove which tool names are developer-declared; it is not a member of `GovernanceEventType`. A single set of event types covers PII, secrets, prompt injection, and any custom guardrail without per-detector event proliferation.

Every one of these lands in `run_events` with the same row shape as a lifecycle event: `sequence_index`, `iteration_index`, `event_type`, `correlation_id`, `data` (JSON), `created_at`. See [Event ordering](/docs/architecture/event-ordering) for how sequencing works.

## Producing and reading a governance event

Turn on a guardrail and the governance events land on the same `run_events` stream you read with `RunStore.get_events`. Here a PII guardrail redacts an email from the incoming message. `PII(engine="presidio")` needs the optional extra (`pip install "dendrux[presidio]"` and a spaCy model); the default regex engine, `PII()`, needs nothing extra:

```python
import asyncio

from dendrux import Agent
from dendrux.guardrails import PII
from dendrux.llm.anthropic import AnthropicProvider
from dendrux.store import RunStore


async def main() -> None:
    url = "sqlite+aiosqlite:///gov.db"

    async with Agent(
        name="Support",
        provider=AnthropicProvider(model="claude-haiku-4-5"),
        prompt="You are a support agent. Reply briefly.",
        guardrails=[PII(engine="presidio")],   # redact PII before it reaches the model
        database_url=url,
        strict_tenancy=False,  # single-tenant example; see Multi-tenancy
    ) as agent:
        result = await agent.run("My email is jane.doe@example.com, can you confirm it?")

    store = RunStore.from_database_url(url)
    async with store:
        for e in await store.get_events(result.run_id):
            print(e.sequence_index, e.event_type)
        # 0 run.started
        # 1 tools.declared
        # 2 guardrail.detected
        # 3 guardrail.redacted
        # 4 llm.completed
        # 5 run.completed


asyncio.run(main())
```

Lifecycle events (`run.started`, `tools.declared`, `llm.completed`, `run.completed`) and governance events (`guardrail.detected`, `guardrail.redacted`) share one ordered stream. Adding `require_approval=[...]` puts `approval.requested` / `approval.decided` on the same stream; `deny=[...]` adds `policy.denied`. See [Approval](/docs/architecture/approval) and [Access control](/docs/architecture/access-control) for runnable examples of those.

## A run that exercises two layers

The scratchpad below builds an agent with PII redaction *and* an approval gate, then runs the input `"Refund order 42 for jane.doe@example.com."` Both layers fire. Real `run_events` from the run (captured on Dendrux 0.5.0 with claude-haiku-4-5):

```text
[lifecycle] seq=0   iter=0  run.started
[lifecycle] seq=1   iter=0  tools.declared        data={"local_tool_names": ["refund"]}
[GOV]       seq=2   iter=1  guardrail.detected    data={"direction": "incoming", "findings_count": 1, "entities": ["EMAIL_ADDRESS"]}
[GOV]       seq=3   iter=1  guardrail.redacted    data={"direction": "incoming", "entities": ["EMAIL_ADDRESS"]}
[lifecycle] seq=4   iter=1  llm.completed
[GOV]       seq=5   iter=1  approval.requested    corr=01M5Y7RAS637MVJRYQ8HENW0YS  data={"tool_name": "refund", ...}
[lifecycle] seq=6   iter=1  run.paused
[lifecycle] seq=7   iter=0  run.resumed
[lifecycle] seq=8   iter=0  tools.declared        data={"local_tool_names": ["refund"]}
[lifecycle] seq=9   iter=1  tool.completed        corr=01M5Y7RAS637MVJRYQ8HENW0YS
[GOV]       seq=10  iter=1  approval.decided      data={"decision": "approved"}
[GOV]       seq=11  iter=2  guardrail.detected    data={"direction": "incoming", "findings_count": 1, "entities": ["EMAIL_ADDRESS"]}
[GOV]       seq=12  iter=2  guardrail.redacted    data={"direction": "incoming", "entities": ["EMAIL_ADDRESS"]}
[lifecycle] seq=13  iter=2  llm.completed
[lifecycle] seq=14  iter=0  run.completed
```

Six governance rows, nine lifecycle rows, one shared `sequence_index` running straight through. A few things worth noting:

1. **Both iterations scanned.** The PII guardrail runs incoming on iteration 1 (the user's original message) *and* iteration 2 (the history replayed to the LLM after the tool result). It catches the email both times and redacts in place. That is fine, the `pii_mapping` is stable so the same replacement token is reused.
2. **Correlation id links the approval to the tool.** `approval.requested` at `seq=5` and `tool.completed` at `seq=9` share the same `correlation_id`. A reader can join the two rows to see "this approval decision authorized this specific tool call." `approval.decided` does not carry the correlation id on this path because it is emitted by the resume endpoint, not by the runner's tool dispatcher.
3. **Lifecycle and governance interleave cleanly.** The run was paused, resumed, and finished; the approval and guardrail events slot into the timeline with their natural iteration numbers. No sorting required.

The `pii_mapping` blob on `agent_runs` after the run:

```json
{
  "<<EMAIL_ADDRESS_1>>": "jane.doe@example.com"
}
```

That mapping is the audit key. Guardrails redact at the LLM boundary only — what the provider API sees. The DB stores raw values (ground truth), and the mapping lets inspection tools you build reconstruct the LLM-eye view from the raw traces on demand. The mapping lives on the `agent_runs` row for the lifetime of the run. See [PII redaction](/docs/architecture/pii-redaction) for the full boundary model.

## How events reach the recorder and notifier

A governance layer does not talk to the DB. It calls `recorder.on_governance_event(event_type, iteration, data, correlation_id=...)` and, through the loop helper, `notifier.on_governance_event(...)` in parallel.

From `dendrux/loops/_helpers.py`:

```python
async def record_governance(recorder, event_type, iteration, data, correlation_id=None):
    """Record governance event to authoritative persistence. Exceptions propagate."""
    if recorder is None:
        return
    await recorder.on_governance_event(event_type, iteration, data, correlation_id=correlation_id)


async def notify_governance(notifier, event_type, iteration, data, correlation_id=None, warnings=None):
    """Notify notifier of a governance event, swallowing exceptions."""
    if notifier is None:
        return
    try:
        await notifier.on_governance_event(event_type, iteration, data, correlation_id=correlation_id)
    except Exception:
        logger.warning("Notifier.on_governance_event failed", exc_info=True)
        if warnings is not None:
            warnings.append(f"on_governance_event failed at iteration {iteration}")
```

Two wrappers, two failure policies. The recorder is fail-closed: if the DB write fails, the run stops. The notifier is fail-open: if a callback raises, the exception is logged as a warning and the run continues. See [Recorder](/docs/architecture/recorder) and [Notifier](/docs/architecture/notifier) for the full picture.

The loop calls both wrappers in sequence at the point where a governance decision is made. A guardrail that redacts emits `guardrail.detected` and `guardrail.redacted` from inside the scan. An approval gate emits `approval.requested` when it decides to pause, and `approval.decided` when the submit endpoint resumes. The pattern is always the same: decide, emit, let the pipeline fan out.

## Detecting changed governance on resume

A paused run can wait for days. In that time someone may deploy a build with a different guardrail list, a looser `deny=`, or a different `before_tool` hook, and the resume then runs under rules the run never started with. Since 0.5.0 Dendrux notices.

At run start it stores a short digest of the governance configuration. On resume it recomputes the digest and compares:

- The digest covers: each guardrail (class name, action and entity set, plus `governance_fingerprint()` if your custom guardrail defines one), the `before_tool` hook's qualified name, the sorted `deny` and `require_approval` lists, and the limits. It never uses reprs or object ids, so it is the same in every process.
- The digest does **not** cover budget numbers: raising a limit to resume a budget pause is a normal operation.
- Runs paused before 0.5 have no digest and are skipped, with a log line.

What happens on a mismatch is your choice:

```python
Agent(..., on_governance_change="warn")    # default in 0.5: emit governance.changed and log; resume proceeds
Agent(..., on_governance_change="raise")   # raise GovernanceMismatchError; the run stays paused
```

`governance.changed` carries `expected_digest`, `actual_digest` and `changed`, the names of the parts that differ (for example `guardrails`, `deny`), never their contents. `GovernanceMismatchError(run_id, expected_digest, actual_digest, changed)` carries the same names. In 0.6 the default becomes `"raise"`; 0.5 prints a `FutureWarning` if you have not chosen. To resume deliberately under new rules, build the Agent with `on_governance_change="warn"`.

## Why one pipeline instead of four subsystems

A reasonable alternative design is to give each governance concern its own audit table. A `guardrail_findings` table, an `approvals` table, a `policy_denials` table, a `budget_events` table. Each concern owns its own schema, its own query path, its own retention.

Dendrux does not do that, for three reasons.

1. **Ordering is important and cross-cutting.** "Did the guardrail detect the PII before or after the approval was decided?" is a question that matters. The answer requires a single ordered log, not four tables that need to be merged on timestamps. `sequence_index` is that log.
2. **Readers want one stream.** An inspection tool that wants to render "what happened on this run" reads one table. An SSE client that wants to stream live events reads one endpoint. A developer who wants to debug a suspicious decision greps one log. Four tables means four queries, four joins, four schemas to learn.
3. **The set of concerns will grow.** MCP events and skill events (seven of them, covering activation, file reads and script runs) were added after the original PII + approval cut. Every addition would otherwise require a new table, a new migration, a new query pattern. A typed event on a shared table needs neither. Adding a new governance concern means adding a new `event_type` constant and calling `recorder.on_governance_event(...)`; everything downstream works.

The cost is a JSON `data` column on `run_events` that is typed per `event_type`, not per column. For a log that readers mostly want in order, that is the right tradeoff. Queries that need a specific event type (`WHERE event_type = 'guardrail.blocked'`) still return the relevant rows in the right order, and the JSON column gives each event type the flexibility to carry whatever payload makes sense without forcing a schema migration.

## Where each concern lives

- Code: `dendrux.guardrails`, `dendrux.runtime.runner` (approval and policy checks), `dendrux.types.GovernanceEventType`
- DB: `run_events.data` (per-event payload), `agent_runs.pii_mapping` (guardrail redaction table)
- Public API: `Agent(guardrails=[...], require_approval=[...], deny=[...], before_tool=..., budget=...)`

Each of the four concerns has its own page: [Guardrails](/docs/architecture/guardrails), [Approval](/docs/architecture/approval), [Access control](/docs/architecture/access-control) (with the [tool policy hook](/docs/architecture/tool-policy)) and [Budget](/docs/architecture/budget). They all share this pipeline.
