# Chatbot threads — history and per-thread observability

A chatbot makes many `agent.run()` calls per conversation — one per user turn. Two things matter for the developer:

1. The agent needs the prior turns of *this* conversation as input.
2. The app needs to ask later: "show me every run that belonged to this conversation" — for cost rollup, audit, support, debugging.

Dendrux gives you both with two existing primitives. No new types, no chatbot subclass.

## Sending history into a turn

[//]: # "docs-test: skip - placeholder database URL, not a real host"

```python
from dendrux import Agent
from dendrux.chat import ChatMessage
from dendrux.types import RunStatus

agent = Agent(
    name="ChatBot",
    provider="anthropic:claude-haiku-4-5",
    database_url="postgresql+asyncpg://...",
    prompt="You are a friendly assistant. Reply briefly.",
)


async def chat_turn(tenant: str, history: list[ChatMessage], user_text: str) -> str | None:
    """Run one turn; record it in ``history`` only when it produced an answer."""
    result = await agent.run(user_input=user_text, history=history, tenant_id=tenant)
    if result.status != RunStatus.SUCCESS or not result.answer:
        return None  # paused or failed: handle it, and keep this turn out of history
    history.append(ChatMessage.user(user_text))
    history.append(ChatMessage.assistant(result.answer))
    return result.answer
```

`tenant` is the tenant of the signed-in user, taken from your authenticated session, never from the request body. Agents enforce tenant scope by default (`strict_tenancy=True`), so a run on a database without `tenant_id=` raises `TenantScopeRequiredError`. An app with no tenants passes `tenant_id=None` explicitly; do not turn `strict_tenancy` off just to shorten the call.

Create the agent once at startup and close it at shutdown with `await agent.close()` (or hold it in `async with Agent(...) as agent:` for the life of the app). It closes the provider and database engine it created.

### History is the previous transcript only

`history=` holds the turns **before** this one. The current message goes in `user_input=`. Do not also append it to `history`: the model would read it twice. If you rebuild `history` from your database on every request, build it **before** you save the new message (or leave that row out), and skip assistant turns that failed or are still streaming. A helper that does this is in [Your app DB vs the Dendrux DB](/docs/recipes/app-database-boundary#the-history-rule).

`ChatMessage` is intentionally narrower than the internal `Message` — only `role` and text (a user turn may also carry images, see [Images](/docs/recipes/images#history-and-follow-up-turns)). Tool calls, call IDs, and runtime metadata are hidden so the dev can't accidentally inject malformed runtime state.

**Storage of the conversation is the dev's job.** Dendrux only reads `history=` as input for the next turn. Persist the chat log in your own table — this preserves the library-not-platform boundary. The chatbot example at `examples/18_chatbot.py` keeps `history` in a Python list; a real app would load it from `messages` in your DB before each turn. For the full picture of which data lives in your DB vs Dendrux's, a minimal app schema, and the per-turn request lifecycle, see [Your app DB vs the Dendrux DB](/docs/recipes/app-database-boundary).

**Tool-using chat?** `history=` carries the question and answer of each turn (not tool calls or tool images), so the model forgets its own tool work between turns and re-explores. Store each turn's `result.run_id` on the thread and pass `runs=thread.run_ids` instead — Dendrux replays the earlier runs' tool calls, results and reasoning from its own traces. See [Memory across runs](/docs/recipes/run-replay).

**With PII guardrails on, your `history` accumulates real names**, not placeholders. The runner deanonymizes `result.answer` on the way back to your code, so appending it gives a natural-language transcript. The DB row keeps the placeholder version for audit. See [PII redaction — user-facing answer](/docs/architecture/pii-redaction#deanonymization-the-user-facing-answer).

## Tagging runs with a thread_id

Pass `metadata={"thread_id": "..."}` on each turn:

[//]: # "docs-test: skip - fragment: relies on `user_text` and `tenant`, defined by setup shown elsewhere"

```python
result = await agent.run(
    user_input=user_text,
    history=history,
    tenant_id=tenant,
    metadata={"thread_id": "thread_abc", "user_id": "u_123"},
)
```

`metadata` is an opaque JSON blob that lands on the run row. Dendrux stores it, never reads it during execution — it's purely for your dev-side queries. The recommended convention for chatbots is `thread_id`; add `user_id`, `channel`, whatever else your domain needs. A tenant written into `metadata` is only a label; the `tenant_id=` argument is what scopes the run.

`thread_id` keys are restricted to `[A-Za-z0-9_-]+` for filter-safety reasons (see below). Use ULIDs, UUIDs, or your own ID format that fits.

## Querying every run in a thread

`RunStore.list_runs(metadata_filter=...)` returns every run whose `metadata` contains all the given key/value pairs (AND across keys):

[//]: # "docs-test: skip - placeholder database URL, not a real host"

```python
from dendrux.store import RunStore

store = RunStore.from_database_url("postgresql+asyncpg://...")  # once, at startup

runs = await store.list_runs(metadata_filter={"thread_id": "thread_abc"}, tenant_id=tenant)
for r in runs:
    print(r.run_id, r.status, r.total_cost_usd, r.created_at)
```

Like the agent, the store lives as long as your app: create it at startup and `await store.close()` at shutdown. The examples below reuse it.

Pass the signed-in user's tenant as `tenant_id=` in every read a user can reach. On the list and detail reads used on this page (`list_runs`, `count_runs`, `get_events`, `get_llm_calls`, `get_tool_invocations`, `get_traces`, `get_pauses`), leaving it out reads **every** tenant's runs, which is only for your own operator tools. Newer reads such as `get_pending`, `follow` and `get_event_view` have no default: pass a tenant, `None` for untenanted runs, or `UNSCOPED` (`from dendrux import UNSCOPED`) for an operator view.

Combines with the existing filters:

[//]: # "docs-test: skip - placeholder database URL, not a real host"

```python
# Only failed runs in this thread
failed = await store.list_runs(
    metadata_filter={"thread_id": "thread_abc"},
    status="error",
    tenant_id=tenant,
)

# Total cost of one user's last 50 turns
runs = await store.list_runs(
    metadata_filter={"user_id": "u_123"},
    limit=50,
    tenant_id=tenant,
)
total = sum(r.total_cost_usd or 0 for r in runs)
```

`count_runs` accepts the same filter — useful for paginated views ("page 1 of 12 turns in this thread").

## Drilling into a single run

Once you have a run from the listing, every other read API on `RunStore` is keyed by `run_id` and works exactly as it does for non-chat runs:

[//]: # "docs-test: skip - fragment: relies on `run`, defined by setup shown elsewhere"

```python
events = await store.get_events(run.run_id, limit=100, tenant_id=tenant)  # event log, first page
llm_calls = await store.get_llm_calls(run.run_id, limit=100, tenant_id=tenant)  # prompts, usage, cache
tool_calls = await store.get_tool_invocations(run.run_id, limit=100, tenant_id=tenant)  # params, results
traces = await store.get_traces(run.run_id, limit=100, tenant_id=tenant)  # ReAct thoughts/actions
pauses = await store.get_pauses(run.run_id, tenant_id=tenant)  # HITL approval cycles
```

The first four reads each return one page of at most 1,000 rows, starting from the oldest: page events with `after_sequence_index`, and traces, LLM calls and tool invocations with `offset` (see [RunStore](/docs/reference/run-store#bounded-list-reads)). `get_pauses` is different: it has no `offset` or cursor and returns its first bounded set of pairs (`limit` defaults to 100); `get_pause_page` returns the same set plus a flag that says whether more exist. Neither pages through a longer pause history. The full audit/tracing surface is available through RunStore; see [Build your own read routes](/docs/recipes/build-your-own-read-routes) — just call it from your own code if you want a custom thread inspector.

## Backend semantics

The filter dispatches by dialect:

- **Postgres**: `meta` is cast to `jsonb` and the predicate is one `@>` containment check covering all keys. Single index-friendly clause regardless of how many keys you filter on.
- **SQLite**: per-key `json_extract(meta, '$.<key>') = ?`. Native types compare correctly; equality works for strings, numbers, and booleans.

Both backends are exercised by the integration test matrix, so the dispatch is locked in.

## What's intentionally not supported in v1

- Nested key paths (`user.profile.id`). Top-level keys only.
- Range queries, partial match, `IN`, `LIKE`. Exact equality only.
- Filtering by absence (`thread_id IS NULL`). Skip the filter — runs without `thread_id` simply won't match a `thread_id=` clause.

If you need any of those, file an issue with the use case. The current shape covers chatbot threads, multi-tenant scoping, and per-user rollup, which is what we've seen real apps want.
