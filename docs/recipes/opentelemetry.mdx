# OpenTelemetry integration

Dendrux ships an `OpenTelemetryNotifier` that emits a small, GenAI-semconv span tree (`invoke_agent` → `chat` → `execute_tool`) onto the host application's existing OTel `TracerProvider`. The host's spans, the host's exporter, the host's backend. Dendrux just plugs into whatever's already wired up.

In 0.6, persisted trace links keep a run in one trace across pause, resume, submit and reclaim, including across processes. Native metrics and log export remain application-owned.

## Status

- **Optional.** OTel is an opt-in extra. Dendrux works the same with or without it.
- **Additive.** No changes to your existing code paths. Pass the notifier in, that's it.
- **Fail-open.** If the OTel SDK or your exporter raises, the run still completes. Observability never kills work.
- **GenAI-semconv targeted.** Uses `gen_ai.operation.name`, `gen_ai.request.model`, `gen_ai.usage.*`. The semconv is still marked Development upstream, so we hold to a stable subset.

## Install

```bash
pip install dendrux[otel]
```

That pulls `opentelemetry-api` only. Your application installs whatever SDK + exporter your stack already uses (`opentelemetry-sdk`, `opentelemetry-exporter-otlp`, the Datadog exporter, the Honeycomb exporter, etc.).

## The single line you add

If your app already has OTel wired up (most do, via the auto-instrumentors for FastAPI / SQLAlchemy / requests / etc.), the entire integration is one extra notifier:

[//]: # "docs-test: skip - fragment: relies on `agent`, defined by setup shown elsewhere"

```python
from dendrux.notifiers.otel import OpenTelemetryNotifier

result = await agent.run(
    "summarize this PDF",
    notifier=OpenTelemetryNotifier(),
)
```

If you're already passing a `ConsoleNotifier`, compose:

[//]: # "docs-test: skip - fragment: relies on `agent`, defined by setup shown elsewhere"

```python
from dendrux.notifiers import CompositeNotifier, ConsoleNotifier
from dendrux.notifiers.otel import OpenTelemetryNotifier

result = await agent.run(
    "summarize this PDF",
    notifier=CompositeNotifier([
        ConsoleNotifier(),
        OpenTelemetryNotifier(),
    ]),
)
```

That is the entire integration. No env vars, no config files, no wrapper classes.

## A self-contained example

Your real app sends spans to its existing exporter. To see the span tree locally without a backend, wire up an in-memory exporter:

```python
import asyncio

from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import SimpleSpanProcessor
from opentelemetry.sdk.trace.export.in_memory_span_exporter import InMemorySpanExporter

from dendrux import Agent, tool
from dendrux.llm.anthropic import AnthropicProvider
from dendrux.notifiers.otel import OpenTelemetryNotifier


@tool(target="server")
async def add(a: int, b: int) -> int:
    """Add two integers."""
    return a + b


exporter = InMemorySpanExporter()
provider = TracerProvider()
provider.add_span_processor(SimpleSpanProcessor(exporter))
trace.set_tracer_provider(provider)


async def main() -> None:
    async with Agent(
        name="Calc",
        provider=AnthropicProvider(model="claude-haiku-4-5"),
        prompt="You are a calculator. Use the add tool.",
        tools=[add],
        database_url="sqlite+aiosqlite:///otel.db",
        strict_tenancy=False,  # single-tenant example; see Multi-tenancy
    ) as agent:
        await agent.run("What is 15 + 27?", notifier=OpenTelemetryNotifier())

    print([s.name for s in exporter.get_finished_spans()])
    # ['chat claude-haiku-4-5', 'execute_tool add', 'chat claude-haiku-4-5', 'invoke_agent Calc']


asyncio.run(main())
```

Children (`chat`, `execute_tool`) finish before their `invoke_agent` parent, which is why they appear first in the exporter's completion-ordered list.

## What you see in your tracing UI

A FastAPI request that calls `agent.run()` produces a tree like this in Jaeger / Honeycomb / Datadog:

```text
POST /runs                                                   1.2s
└─ invoke_agent  [my_research_agent]                         1.1s
   ├─ chat  [claude-sonnet-4-6]                              340ms
   │   gen_ai.usage.input_tokens: 1240
   │   gen_ai.usage.output_tokens: 87
   │
   ├─ execute_tool  [web_search]                             420ms
   │   dendrux.tool.name: web_search
   │   dendrux.tool.success: true
   │
   └─ execute_tool  [pdf_extract]                            55ms
```

The `POST /runs` span comes from your FastAPI auto-instrumentation. The `invoke_agent` span attaches to it automatically because the OTel notifier respects whatever span is currently active when `agent.run()` is called.

## Span shape

Three span types cover the surface:

| Span name              | Operation                  | Notable attributes                                                                  |
| ---------------------- | -------------------------- | ----------------------------------------------------------------------------------- |
| `invoke_agent <name>`  | The whole agent run        | `gen_ai.agent.name`, `dendrux.framework`, `dendrux.run.id`, `dendrux.run.status`    |
| `chat <model>`         | One LLM call               | `gen_ai.request.model`, `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`   |
| `execute_tool <tool>`  | One tool execution         | `dendrux.tool.name`, `dendrux.tool.call_id`, `dendrux.tool.success`                 |

## One trace per run

A run that pauses closes its `invoke_agent` span with the paused status. Dendrux persists the notifier's validated W3C trace link. A resume, submission or reclaim opens a fresh `invoke_agent` span parented to that saved context, so the spans share a trace even in another process. Supply `OpenTelemetryNotifier` on each execution entry point; configure an exporter in each process. Runs without a stored link use the available incoming context.

A delegated child's first span is parented to the active parent tool span when that context is available from the OpenTelemetry notifier; otherwise it uses the parent run link. A custom notifier can supply the optional `trace_link(run_id)` and `current_span_link(run_id, tool_call_id)` seams. Invalid stored links are discarded.

Run spans close as `ERROR` for `error`, `max_iterations` and `cancelled`, including a guardrail stop. Paused runs close normally and get another span when continued. One trace per run means related execution spans, not a span held open while waiting for a person.

## Governance events

Whenever the loop fires a governance event (`policy.denied`, `approval.requested`, `approval.decided`, `budget.threshold`, `budget.exceeded`, `guardrail.detected`, `guardrail.redacted`, etc.), the notifier attaches it as an OTel **span event** on the active `invoke_agent` span. Each event carries `dendrux.governance.*` attributes for whatever scalar data the loop emitted.

This means a single click in your tracing UI shows the full audit story for a run, in temporal order, alongside the spans.

## Failure semantics

| Failure                  | Span behavior                                                                |
| ------------------------ | ---------------------------------------------------------------------------- |
| Tool returns `success=False` | `execute_tool` span closes with `Status.ERROR`; `dendrux.tool.success=false` |
| Provider raises          | `chat` closes with `Status.ERROR` and safe mapped error fields; no vendor message or traceback |
| Run errors out           | `invoke_agent` closes with `Status.ERROR`; non-provider errors include exception type and a frame-only stack |
| Run finishes with `RunResult.error_info` | `invoke_agent` closes with `Status.ERROR` (it was `OK` before 0.5.0), the safe `dendrux.error.*` attributes (category, retryable, status code and so on) and a `provider.error` span event. No vendor text is recorded. Update dashboards that counted these runs as successful |
| Stream consumer abandons | `invoke_agent` closes with `dendrux.run.status=cancelled` and span status `ERROR`; any in-flight `chat` / `execute_tool` spans get swept and marked ERROR with `dendrux.span.orphan_close_reason` |

That last row is the subtle one. Stream cancellation (`asyncio.CancelledError`, `GeneratorExit`) is a `BaseException` and bypasses the loop's `except Exception` paths, so `on_llm_call_completed` / `on_llm_call_failed` may not fire. The notifier sweeps any open child spans on the run-level terminal hook so they never leak as never-ending operations in your backend.

## Safe defaults

By default, no prompt content, completion text, or tool arguments are captured as span attributes. Only IDs, names, model, token counts, and statuses go on the wire.

Two opt-in flags exist for power users / debugging:

```python
OpenTelemetryNotifier(
    include_tool_params=True,    # adds dendrux.tool.params (JSON) to tool spans
    include_messages=True,        # adds gen_ai.completion to chat spans (completion text only)
)
```

Both capture content beyond the default telemetry fields. Enable them only in trusted environments with application-owned data controls. Prompt capture is not implemented.

Dendrux reports a fixed list of provider error codes; unknown codes become `provider_unknown`. Non-provider exception stacks contain file, line and function only, without messages or locals. A failed tool's stack shows where Dendrux reported the failure, rather than where the tool itself crashed.

## Concurrent runs

Span lookup is keyed by `run_id` (and `(run_id, tool_call.id)` for tool spans). One `OpenTelemetryNotifier` instance can be shared across many concurrent runs without any contextvar gymnastics or cross-contamination.

## Worked end-to-end example

`examples/21_otel_complete_cycle.py` runs a 7-stage tour exercising every notifier hook (streaming tools, deny, approval pause/resume, sync rejection, client-tool resume, budget cap, PII guardrails) and prints a per-stage Rich tree of every span emitted, plus a final invariants check:

```text
total spans                          37
invoke_agent spans (root-of-run)     10   ← matches on_run_started=10
chat spans                           16   ← matches on_llm_call_started=16
execute_tool spans                   11   ← matches on_tool_started=11
ERROR-status spans                    1
orphan-closed spans                   0
governance span events               13   ← matches on_governance_event=13

invariant                               violations  status
invoke_agent has framework + run.id              0  ✓
chat / execute_tool has live parent              0  ✓
chat has both usage attrs (or neither)           0  ✓
orphan-closed spans are ERROR                    0  ✓
```

Re-run this after any change to the notifier, the runtime lifecycle, or your loop implementation. If the invariants table flips red, OTel output regressed.

## What is not covered

This integration ships a small surface that covers the most common need. The remaining items are **deferred, not forgotten**. They will be reconsidered when real usage surfaces a need.

- **Native metrics signal.** OTel metrics for token usage, tool call counts, run duration, etc. are not emitted natively. Most backends derive these from spans for free. Native counters / histograms may land later for cardinality control.
- **Native log signal.** `LoopRecorder` is Dendrux's audit source of truth. Routing the same events out as OTel logs is possible but creates two sources of truth; if you want log/trace correlation, the recommended path today is a downstream exporter that reads sanitized recorder events.
- **Prompt capture.** `include_messages=True` captures completion text only. Capturing prompts requires JSON-serializing multimodal and tool-call content correctly, with size guards.
- **`auto_instrument()` helper.** There is no one-call hook that installs the notifier globally. Pass it explicitly per `agent.run()` call. A helper may follow if usage demands.

The application continues to own exporters, sampling, metrics and log correlation. Durable trace continuity does not install an exporter or keep a worker alive across a pause.
