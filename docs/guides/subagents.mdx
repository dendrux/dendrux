# Managed subagents

A subagent is a tool backed by a fresh child run. The parent's model calls it by name with one required string argument, `task`. The child uses its own provider, prompt, tools and conversation. It sees the task brief, not the parent's conversation. Its answer becomes a tool result for the parent.

The call is blocking. The parent run pauses in the database while the child works. Your `run()` call returns when the workflow finishes or needs an external answer. The parent takes its next model turn after its children finish. Each call starts a new child run. When the model calls several subagents in one response, they run in parallel (see [Parallel subagents](#parallel-subagents)). There are no background children that outlive the parent's turn.

## Register and run

Pass child Agents in `subagents=[...]`. Each child needs a provider, a valid tool name and a non-empty `description`. A name must start with an ASCII letter or underscore. Use only ASCII letters, digits and underscores, with at most 64 characters. The description tells the parent's model when to use that child. Sibling names must be unique and must not clash with the parent's tools. Registration cycles are refused.

This example asks a reviewer to check a draft. Its word-count tool needs approval. Your application supplies `decide(pending)`: an async function that authorizes the actor, displays the pending action, and returns their decision. A web service can return the pause to the client and submit the decision in a later request instead.

[//]: # "docs-test: skip - exercised by test_guide_subagents.py with SQLite, mock providers and an application decision callback"

```python
from dendrux import Agent, tool
from dendrux.store import RunStore


@tool()
async def count_words(text: str) -> int:
    """Count the words in a draft."""
    return len(text.split())


async def review_report(
    database_url,
    tenant_id,
    decide,
    *,
    lead_provider="anthropic:claude-haiku-4-5",
    reviewer_provider="anthropic:claude-haiku-4-5",
):
    async with Agent(
        name="reviewer",
        description="Review one draft and return a short assessment.",
        provider=reviewer_provider,
        prompt="Check the draft. Use count_words before reporting.",
        tools=[count_words],
        require_approval=["count_words"],
    ) as reviewer, Agent(
        name="lead",
        provider=lead_provider,
        prompt="Ask reviewer to check the draft, then summarize its assessment.",
        subagents=[reviewer],
        database_url=database_url,
    ) as lead:
        result = await lead.run("Review this draft: Sales rose.", tenant_id=tenant_id)
        pending = result.pending
        if pending is not None and pending.kind == "approval":
            approved = await decide(pending)
            result = await lead.submit_approval(
                result.run_id,
                approved=approved,
                expected_pause_id=pending.pause_id,
                tenant_id=tenant_id,
            )

        async with RunStore.from_database_url(database_url) as store:
            tree = await store.get_subtree(
                result.run_id, tenant_id=tenant_id, max_nodes=1000,
            )
        # Return other pause kinds and any later approval for the application to handle.
        return result, tree
```

Call `review_report` with your database URL, the authenticated tenant and your decision function. It returns the root result and a subtree usage snapshot. A model can ask for more work or another approval; if `result.pending` is set again, handle that next pause through the same root id.

Managed runs need persistence with format-2 checkpoints and the `managed_subagents` store capability. SQLite supports this example. See [Managed subagent stores](/docs/reference/state-store#managed-subagent-stores) for built-in declarations and custom-store requirements. A missing capability or required durability flag raises `StoreCapabilityError` before managed execution begins.

## Parallel subagents

A model fans out by returning several subagent calls in **one response**. Dendrux creates all the children together, runs them at once, and gives the parent one model turn after every child has finished. Server-tool calls in the same response finish first, before any child starts, even if the model listed a child first. Your prompt has to ask for it: tell the lead to call the independent subagents together in one step. The same child may be called twice in one response, each call with its own task; each call is its own child run.

| Rule | Value |
| --- | --- |
| Most subagent calls per response | `Limits.max_parallel_subagents`: default 4, from 1 to 32 (`MAX_PARALLEL_SUBAGENTS`) |
| Larger batch | The **whole** batch is refused before any effect, including the calls that would have fit. Code `managed_fanout_limit` |
| A subagent call beside a client-tool or human-input call | The whole batch is refused. Code `managed_batch_unsupported` |
| A name in `exclusive_subagents=[...]` called with another subagent | The whole batch is refused. Code `managed_batch_unsupported`, reason `exclusive` |
| One subagent call (any name), with no client-tool or human-input call beside it | Allowed |

A refusal is a failed tool result for every call in the batch, so the model can try again. For `managed_fanout_limit` the result names the number requested and the limit and says to call at most that many at once; the code is the same in tool results, events and logs. Raise the limit on the root Agent with `limits=Limits(max_parallel_subagents=8)`. A non-default value is part of the run's governance snapshot, so changing it while a run is paused is a governance change on resume (see [Governance](/docs/architecture/governance#detecting-changed-governance-on-resume)).

Use `exclusive_subagents=["publisher"]` for a child that must never run beside another child, such as one with side effects. Call order is fixed by the saved bindings, so results, pauses and events come back in the order the model emitted the calls, not the order the children finish.

Parallelism needs a store that declares the `managed_fanout` capability: the built-in SQLite, PostgreSQL, MySQL and MariaDB stores do. On a store without it the effective limit is 1, and a second call in one response is refused with `managed_fanout_limit` (the log line has `store_capability=false`). See [Capability matrix](/docs/reference/state-store#capability-matrix).

Nesting multiplies concurrency: a child that fans out has its own limit. The overall bound is the per-workflow `Limits.max_managed_runs` (default 128).  Every child is a real run in the same store with its own database work, so size your connection pool for the number you run at once.

Usage and budget are aggregated over the whole tree; see [Root budget](#root-budget). `result.usage` is still the root only, and `get_subtree` gives the total.

The parent's deny rules, approval rules and tool hook apply to the delegation call. The child's own rules govern its work. Registering a child does not copy the parent's prompt, tools or guardrails. Configure each child's data policies explicitly. Treat its report as tool data.

### Approvals beside a subagent call

A response can hold a subagent call and a server call that needs approval. The root then pauses for approval of the batch. Approving runs the server call first and then binds the child. Denying only the server call records the denial and still runs the child. Rejecting the whole batch with `approved=False` denies the subagent call too, and no child run is created.

**Subagent calls are not approval-gatable in 0.8.** `require_approval=` cannot name a subagent, and a `before_tool` hook that answers `require_approval` for a subagent call is treated as a denial. Gate the child's own tools instead.

A subagent call is never a client-tool call. Only its child run reports it. `submit_tool_results` (or `resume` with `tool_results=`) that carries a result for a subagent call raises `ManagedResultRefusedError`, code `managed_result_refused`, and changes nothing.

## Store, tenant and depth

A child without a store borrows the root's resolved store for that invocation. The Agent template is not changed. If a child has an explicit `state_store=`, it must be the same store object as the root's. Matching database URLs are not enough. Leave `database_url=` off registered children, as in the example, or build one shared store and pass it to every Agent.

Every child inherits the root run's actual tenant. Pass `tenant_id=` on every run, continuation and read. Rebuild the same named registrations and shared store configuration after a restart so the root Agent can resolve the saved child path.

The root is depth zero. The default `max_delegation_depth` is 10. Set it on the root Agent to change the ceiling; zero allows no child calls and explicit `None` removes the depth ceiling. A child's own numeric limit can tighten the ceiling for its subtree. Definitions and runtime calls are both checked. A runtime depth overrun raises [DelegationDepthExceededError](/docs/reference/errors#also-exported-from-dendrux).

More than 10 direct children logs a warning. `Limits.max_subagent_definitions` (default 256) caps the expanded definition tree and counts the root itself, so the default allows 255 subagent definitions below one root. An Agent used in two places counts twice. Set the limit on the root Agent's `limits=`.

## SingleCall subagents

A child can use `loop=SingleCall()`. It runs one model step and never pauses, so it has no tools and no subagents of its own. Normally that step is one provider call; an image retry may make a second provider attempt. Its answer is the report the parent sees. A parent must use ReAct; a `SingleCall` agent with subagents raises `SubagentDefinitionError(reason="single_call_parent")`.

With `output_type=`, the report is the validated value as compact JSON. Use `run()` for such a workflow; streaming refuses a child with `output_type`. A value that fails validation fails the child, and the parent sees `managed_child_failed`. A child that sets both `guardrails` and `output_type` is refused with `ValueError` when the root run starts, before anything is written. If the definition changes after the root started, for example by a redeploy while the root was paused, the next delegation is refused the same way before its bind: no child run is created and the root run ends `error`. Fix the definition and start a new run.

### An interrupted SingleCall child fails

Dendrux never runs an interrupted `SingleCall` child again. If the process dies during its model step, the child stays `running` until you call `sweep()`. The sweep finalizes it as `error` with `failure_reason="stale_running"`, or `"never_started"` if it died before it started. This happens with every `on_stale` setting, and the child is never listed in `reclaimable`. A provider error fails the child too.

The parent sees an ordinary failed tool result with code `managed_child_failed`, the same code as a model or provider error. Read the child run's `failure_reason` to tell a crash from a model error. The parent's model may choose to delegate again; that starts a new child run.

`SweptRun` names the child, not the root. Walk `parent_run_id` up to the root and reclaim the root, which adopts the failure and continues the parent:

[//]: # "docs-test: skip - exercised by test_guide_subagents.py with a crashed SingleCall child on SQLite"

```python
from datetime import timedelta

from dendrux import sweep

swept = await sweep(
    database_url=database_url, stale_running=timedelta(minutes=5), on_stale="reclaim"
)
async with RunStore.from_database_url(database_url) as runs:
    for item in swept.stale_running:
        run = await runs.get_run(item.run_id)
        while run is not None and run.parent_run_id is not None:
            run = await runs.get_run(run.parent_run_id)  # bounded by the delegation depth
        if run is not None and run.run_id != item.run_id and run.agent_name == lead.name:
            await lead.reclaim(run.run_id, tenant_id=run.tenant_id)
```

A token-less `resume` on the root adopts the failure the same way. Before the sweep, `reclaim` on the root raises `RunNotReclaimableError(reason="loop_unsupported")` with the child's run id: it means "run `sweep()` first, then reclaim the root again", not that the workflow is lost. Submit and token-bearing resume calls raise `RunNotPausedError` while the child is running.

### Known limits

- A sweep cannot tell a dead process from a live one that lost its database connection. If a child's call is cut off from the database, the sweep fails the child and its writes are fenced. The call itself can still complete and be billed by the provider, but its usage is never recorded, so the root budget can undercount by that one call. The same applies to a ReAct child's in-flight call. Keep `stale_running` well above the lease interval.
- A root `request_pause` sent while a `SingleCall` child's call is in flight has no effect: the child finishes and clears the request, and the parent continues. `PauseOutcome.affected` still lists the child as `requested`. Cancel instead, or request the pause again. A ReAct child's final model call has the same gap.
- The child's call counts toward the root budget. The child's own `budget.*` events are advisory (`action="warn"`); the parent enforces the root budget at its next checkpoint, after it adopts the report. The overshoot is at most the child's one run, which can be two provider attempts when an image retry fires.
- Cancelling the root while the child's call is in flight is cooperative, even in the process that owns the run: the call finishes, its report is not adopted, and the root ends cancelled. Cancelling the task that awaits `run()` interrupts the call instead; the child ends `cancelled`, and the root later adopts `managed_child_cancelled`.

## Answer a child pause through the root

Approval, client-tool, human-input and requested pauses inside a child surface on the root. The result keeps the root's `run_id` and reports the child's waiting status. For example, an approval returns `waiting_approval`, not the parent's internal managed wait.

The root-facing `pending` includes:

| Field | Meaning |
| --- | --- |
| `run_id` | The root id to use for continuation |
| `pause_id` | The active child's pause token |
| `agent_name` | The child that needs an answer |
| `agent_path` | Names from the root to that child, such as `["lead", "reviewer"]` |
| `origin_run_id` | The child's run id, for reads and diagnostics |

After a restart, reload the pause before displaying the action:

[//]: # "docs-test: skip - exercised by test_guide_subagents.py with store, root_run_id and tenant_id"

```python
pending = await store.get_pending(root_run_id, tenant_id=tenant_id)
```

Authorize the actor for the displayed action in your own route. Submit to the root id with `expected_pause_id=pending.pause_id`. Managed continuations always require the token, including when strict tenancy is disabled. A stale token is refused; do not silently replace it with a newer token and retry the old decision.

| Pending kind | Root Agent method |
| --- | --- |
| `approval` | `submit_approval` |
| `client_tool` | `submit_tool_results` with the child's displayed call ids |
| `input` | `submit_input` |
| `paused` | `submit_resume` or an allowed `resume` / `resume_stream` |

The child validates the submission using its own tools and limits. When it finishes, the saved answer returns to its parent and execution continues up to the root. The call returns the root's result or the next pause. A failed child becomes a failed tool result with code `managed_child_failed`; it does not count as root success. `resume` can adopt an already terminal child without a pause token when no external answer is needed.

The parent's `Limits.max_tool_result_bytes` caps the report's serialized UTF-8 payload, including after a result transform. The default is 1 MiB. An oversized report becomes a failed tool result with code `managed_report_too_large`, without partial report text.

Direct child control is refused with `managed_root_required`. Child reads are allowed. `request_pause` on the root reaches the active branch. A note submitted to the root waits until the root next executes; it is not forwarded to the child.

## Several paused subagents

With parallel children, more than one can need an answer at once. The root's result keeps the root's `run_id`, and `result.pending` is the first pause. `result.pendings` lists all of them, depth first, siblings in the order of the model's calls (empty when nothing waits, on every result path), for a workflow with up to 257 active runs (see [The pending read bound](#the-pending-read-bound)). Each continuation names its pause with `expected_pause_id=`: submit to the **root id** with the token of the leaf you are answering. A token that is not currently held raises `PauseStatusMismatchError(reason="pause_id")` and carries `current_pause_id`, the first pending pause; nothing is claimed.

Answer the pauses in a loop until none is left. This runs on a scripted model, with two children that each need an approval:

```python
import asyncio

from dendrux import Agent, tool
from dendrux.testing import FakeModel, call, calls, say


@tool()
async def refund(order_id: int) -> str:
    """Refund an order."""
    return f"refunded {order_id}"


script = FakeModel(
    {
        "lead": [
            calls(call("billing", task="Refund order 1"), call("shipping", task="Refund order 2")),
            say("Both refunds are done."),
        ],
        "billing": [call("refund", order_id=1), say("Order 1 refunded.")],
        "shipping": [call("refund", order_id=2), say("Order 2 refunded.")],
    }
)


async def refund_both() -> str | None:
    desks = [
        Agent(
            name=name, description=f"The {name} desk.", provider=script.provider(name),
            prompt="Refund the order.", tools=[refund], require_approval=["refund"],
        )
        for name in ("billing", "shipping")
    ]
    async with Agent(
        name="lead", provider=script.provider("lead"), prompt="Ask both desks together.",
        subagents=desks, database_url="sqlite+aiosqlite:///refunds.db",
    ) as lead:
        result = await lead.run("Refund both orders", tenant_id="acme")
        assert len(result.pendings) == 2
        while result.pendings:
            pending = result.pendings[0]  # which desk is pending.agent_name; ask your approver here
            result = await lead.submit_approval(
                result.run_id,
                approved=True,
                expected_pause_id=pending.pause_id,
                tenant_id="acme",
            )
        return result.answer


assert asyncio.run(refund_both()) == "Both refunds are done."
```

- **After a restart,** `await store.get_pendings(root_id, tenant_id=tenant_id)` rebuilds the list (see [RunStore](/docs/reference/run-store#pending-and-live-reads)). `RunStore.from_database_url(...)`, `from_engine` and a store you build yourself all work for it.
- **A budget pause makes one pause per child.** When a root budget is breached with `on_exceed="pause"`, every ReAct leaf that observes the breach creates its own pause. How many there are (one to the number of children) depends on timing, so write the loop above rather than answering once. Each is resumed through the root with its own token. Read the reason on `pending.reason`.
- **Token-less `resume(root)`** reconnects a workflow whose children have all finished, the same way `reclaim(root)` does. It is refused while any leaf is externally paused, even if other children are terminal: answer the pauses first, or call `reclaim` to read the workflow without answering.
- **Telling "working" from "paused".** While children are running and nothing needs a person, the root's stored status is `paused`, `get_pending` returns `None`, and `get_result` reports the run as running. Use `RunSummary.waiting_for == "subagents"` or `list_runs(include_waiting=False)` to keep those runs out of a "needs attention" list; see [RunStore](/docs/reference/run-store#telling-a-persons-turn-from-a-subagent-wait).
- **Replayed approvals.** After a crash, a tool call that was not marked `idempotent` and may have run is not run again silently: it comes back as a root approval pause with `source=recovery`. Its arguments can be hidden (`args_hidden`); resolve it on the server rather than approving an empty object.

### Finding runs that need a person

A parent that waits on its subagents stays `waiting_for="subagents"` even when one of its children needs an approval, so `list_runs(status="paused", include_waiting=False)` can leave out a workflow that needs a person. A run that is paused directly has its own status instead. To build an inbox, page through every status that can need a person, keep the roots, and ask each root for its pauses:

[//]: # "docs-test: skip - fragment: relies on `runs` and `tenant_id`, defined by setup shown elsewhere"

```python
NEEDS_ATTENTION = ["paused", "waiting_approval", "waiting_human_input", "waiting_client_tool"]


async def inbox(runs, tenant_id):
    offset = 0
    while True:
        page = await runs.list_runs(
            status=NEEDS_ATTENTION, tenant_id=tenant_id, limit=50, offset=offset
        )
        for root in (r for r in page if r.parent_run_id is None):
            for pending in await runs.get_pendings(root.run_id, tenant_id=tenant_id):
                yield root.run_id, pending
        if len(page) < 50:
            return
        offset += 50  # the list offset is capped at 10,000: narrow by time for larger inboxes


async for root_id, pending in inbox(runs, tenant_id):
    if pending.kind in ("approval", "input", "paused"):
        ...  # route to a person; answer through root_id with pending.pause_id
    elif pending.kind == "client_tool":
        ...  # route to the client that runs the tool
```

A root that is a plain pause gives one item; a root that only waits on running children gives an empty list. Answer each item through the root id with its `pause_id`, as above.

#### The pending read bound

`get_pendings`, `get_pending` and the paths that rebuild that view (`get_result` and reconnects through `reclaim`) walk at most 257 active nodes, the root included, in one pass. A legal workflow whose active tree is larger (for example after raising `Limits.max_managed_runs`) makes those reads raise `ManagedStateError(reason="binding_conflict")` instead of returning every pause. A summary read such as `get_subtree`, and cancellation, use other paths and are not limited this way.

## Streaming and events

Use `stream` to drive the same workflow while reading the root's text:

[//]: # "docs-test: skip - exercised by test_guide_subagents.py with a configured lead Agent and tenant_id"

```python
async with lead.stream("Review this draft: Sales rose.", tenant_id=tenant_id) as stream:
    async for text in stream.text():
        print(text, end="")
    result = stream.result
```

Only root text appears in answer deltas. When you iterate the full stream instead of `stream.text()`, child tools yield `tool_use_start`, `tool_use_end` and `tool_result` events. They carry the child's `run_id`, tool name, call id and outcome information, without arguments or output. The root's subagent-call events also omit the task brief and report. The final `result.steps` contains the root's own steps, including its subagent calls. `resume_stream` accepts the root id and the `expected_pause_id` of any paused child, and a held approval batch with several subagent calls can be resumed on a stream. Closing a workflow stream early requests cancellation with cascade: every child stops at its next checkpoint, owner tasks are joined and nothing is left `running`.

Parallel children stream at the same time. When one child pauses while its siblings keep working, the full stream yields a non-terminal `RunEventType.SUBAGENT_PAUSED` event with the origin child's `run_id`, its `pause_id`, and a tuple of `call_ids`. The stream continues until the root pauses or finishes. The terminal `RUN_PAUSED` event carries the full `run_result`. For a client-tool pause, its pending calls include the tool names and arguments the client needs. To read a child’s pause while siblings are still running, call `store.get_pendings(root_id, tenant_id=tenant_id)` and match the origin and pause IDs, or use `store.get_pending(child_id, tenant_id=tenant_id)` and check its pause ID. Child tool progress is live. Events pass through one bounded queue (256), so a slow consumer slows the children down instead of growing memory.

Each run keeps its own durable event log. The parent's `tool.started` event records the delegation's `child_run_id` and `agent_path`. At adoption, `tool.completed` includes `managed_outcome="succeeded"`, `"failed"` or `"cancelled"`. Completion alone does not mean success. These delegation lifecycle payloads contain ids, paths and outcome information, without task or report text.

Use `RunStore.follow(root_run_id, tenant_id=tenant_id)` for a client event feed. Follow the `child_run_id` separately for child detail. There is no combined subtree feed. See [read routes](/docs/recipes/build-your-own-read-routes) for cursors and feed handling.

A call-level `notifier=` also receives child callbacks with each child's `run_id`, on initial and continuation calls. Delivery is best effort. Supply the notifier again after a restart. Durable integrations consume saved events and deduplicate them; callbacks have no exactly-once guarantee.

## Usage and release work

`result.usage` is local to the root run. In the example, `tree.usage` totals the root and its descendants. Each `tree.nodes` entry has that run's own `usage`. Reading the tree while paused gives usage recorded so far. Pass a finite `max_nodes=` bound when calling `RunStore.get_subtree`; reaching that descendant bound raises `SubtreeTooLargeError`.

## Cancellation

Cancelling a managed root always reaches its managed descendants, whatever `cascade=` says; `cascade=True` also includes legacy descendants. Descendants settle deepest first and the root last. A paused descendant is finalized `cancelled` at once. A running one gets a cancellation request and stops at its next checkpoint. Cancellation is cooperative: it cannot undo effects that already happened.

`result.meta["cascade"]` lists each reached run with its `run_id` and an `outcome`: `cancelled`, `cancel_requested` (running; stops at its next checkpoint), `terminal` or `skipped`. A child whose saved managed header is corrupt is skipped, logged with code `cascade_child_skipped`, and marks the walk truncated. The walk is also bounded by `Budget.max_subtree_nodes` (default 10,000). When `result.meta["cascade_truncated"]` is true, call `cancel_run(root_id)` again after fixing the cause; a repeat call walks the descendants again even when the root is already terminal.

A cancelled child becomes a failed tool result with code `managed_child_cancelled`, and the parent's `tool.completed` event carries `managed_outcome="cancelled"`.

With parallel children the same rules hold, with these timings:

- The root is cancelled at once; children in any process notice the durable stop at their next checkpoint. A child inside a long tool call settles only when that tool returns, so allow for your slowest tool. Cancellation does not confirm that an in-flight provider call has stopped.
- A success committed before the cancel mark stays successful. A `SingleCall` child that has already started has no later checkpoint and may finish successfully; the root stays cancelled and is not revived.
- A batch bind that races the cancel creates all of its children or none.
- After the root is cancelled, a pause token saved from one of its leaves can no longer resume the workflow: a submit through the root raises `RunAlreadyTerminalError` and writes nothing.
- If a cascade fails partway, or the process that owned the workflow died, call `cancel_run` on the root again. Running children still stop at their checkpoints; a child or root that is paused stays paused, with its cancel request set, until a later `cancel_run` settles it. Dendrux runs nothing in the background to do this.
- Cancelling the task that awaits `run()`, or closing a stream, cancels the owner tasks and joins them before returning, and `CancelledError` propagates.

Without an `Agent` (an admin route or CLI), use [`dendrux.cancel_run`](/docs/recipes/cancel-run#cancel-a-run-without-an-agent). It needs the root run id, `tenant_id=` and a store.

`request_pause(root)` flags the whole bound workflow, deepest first, even with `cascade=False`. Every running ReAct leaf pauses at its next checkpoint and appears in `pendings`; `SingleCall` children ignore a requested pause and finish their one call. A request does not revoke any running claim. Continue a pause through the root with that leaf's token. A remote controller needs the same registered subagent definitions as the process that started the workflow.

## Root budget

A root `budget=` counts the root and every descendant together; children never get a fresh allowance. The parent checks the root's rolled-up usage once before it binds a batch; an enforcing breach admits no child from that batch. Each executing ReAct leaf checks the same rollup at its iteration checkpoints, including its siblings' flushed usage, and a `SingleCall` child's usage is checked when the parent adopts its report. In-flight provider calls are not counted yet. A registered child's own `budget=` is refused with `ManagedBudgetConfigurationError` (code `managed_budget_invalid`) when the Agent is built. A root budget with `include_children=False` is refused the same way.

The budget is a soft limit on iterations, not a hard money cap. Before every executing leaf has observed a breach, each simultaneously executing leaf in the whole tree can make up to one more unchecked provider iteration, plus the root's own; parked ancestors make none. A `SingleCall` is one call and cannot stop mid-call. Nesting multiplies the number of parallel leaves, bounded by the per-parent limit and the workflow's run cap. `on_exceed="cancel"` stops children at their next checkpoint and leaves the root cancelled with the budget details; `"warn"` emits budget events and continues; `"pause"` makes one pause per leaf that observes the breach (see [Several paused subagents](#several-paused-subagents)).

With a cost limit and `on_exceed="pause"` or `"cancel"`, an unpriced call anywhere in the tree stops the workflow with reason `unpriced_call`; resume through the root to accept it. If a descendant's usage cannot be established at all (the provider reported no usage, a usage write failed, or the rollup read failed), the root stops with `managed_usage_unknown` according to `on_exceed`. Raise the budget and resume through the root to continue. With `on_exceed="warn"`, or without a cost limit, neither case stops the workflow.

## Run and definition limits

`Limits.max_managed_runs` (default 128) bounds the runs one workflow may create, counting the root and finished children. The cap is saved in the root's first checkpoint, so changing `limits=` later does not change a running workflow. A bind past the cap is refused before any write: the call raises an error with code `managed_run_limit` (on a stream, the result ends `error`), and no child run is created. Each bind counts the existing runs up to the cap, so a higher cap makes each bind cost more.

`Limits.max_subagent_definitions` (default 256, root included) bounds the registered definition tree; see [Store, tenant and depth](#store-tenant-and-depth).

## Recovery through the root

Control a managed workflow only through its root id. `resume`, `submit_*`, `reclaim`, `cancel_run` and `retry` on a child id raise `ManagedChildControlError` (code `managed_root_required`). Reading a child is allowed.

After a crash, call `sweep(on_stale="reclaim")` and then `reclaim` on the root id. The root walks its saved bindings: a finished child is adopted without running again, and a running ReAct child is reclaimed under the usual lease rules once the sweep has marked it. A healthy child that is still running in another process is never taken over. `SweptRun` and `ReclaimableRun` name the child; walk `parent_run_id` up to the root, as in the SingleCall example above.

With parallel children, `reclaim(root)` validates the saved bindings and reconnects every branch: finished children are left untouched, swept ReAct children are reclaimed, owner tasks are joined, and the parent adopts once. A child that is still live under its lease stays with its owner, and a running `SingleCall` child waits for a developer-called `sweep()`; a root that is not in that state is never rerun. Terminal children are never run twice. A result transform may run again for a call whose observation did not commit before the crash, so keep transforms pure or idempotent.

`sweep()` can also tell you which roots are ready. Pass `adoptable_after=timedelta(...)` and `result.adoptable` lists the root ids of managed waits older than that age whose children are all terminal, even with `abandoned_waiting` omitted. Sweep only lists them: it never adopts, drives or abandons a workflow, and the age never shortens ordinary abandonment. Call `agent.reclaim(root_id, tenant_id=root_tenant)` for each one, with the matching definitions, and keep the same thresholds when you continue with `cursor=result.cursor`. The scan is native to the built-in SQL stores; a custom store without it raises `NotImplementedError` before anything is scanned or marked. Listing shares the `max_runs` cap with the waiting scan.

**Upgrading.** Running 0.7 and 0.8 workers on the same database at the same time is not supported: 0.8 may write a parallel wait that 0.7 cannot read, and 0.7 refuses it with `ManagedStateError(reason="wait_invalid")`. ## Current limits

- Managed parents must use ReAct. Children use ReAct or `SingleCall`; any other loop is refused with `SubagentDefinitionError(reason="loop_unsupported")` before execution. A paused child continues only on ReAct, so re-registering it as `SingleCall` while it waits is refused the same way.
- Cancelling the root while a subagent's call is in flight is cooperative, even in the process that owns the run: the call finishes, its report is not adopted, and the root ends cancelled. Cancelling the task that awaits `run()` interrupts the call instead.
- A root `request_pause` sent while a `SingleCall` child's call is in flight has no effect.
- A live child that lost its database connection can be swept while its call completes; the call is billed but not recorded, so the root budget can undercount by that one call.
- A `SingleCall` child's own budget events are advisory; the parent enforces the root budget.
- Streaming refuses registered subagents with guardrails or `output_type`. Use `run()` for a workflow with child guardrails or a structured `SingleCall` child.
- `retry` on an Agent with managed subagents is refused. Continue paused work through the root's resume or submit methods.
- Subagent calls are not approval-gatable in 0.8; gate the child's tools.
- A fan-out is limited by `Limits.max_parallel_subagents` (at most 32) and needs a store with the `managed_fanout` capability.
- A failed child shows the parent only `managed_child_failed`; read the child run's `failure_reason` for the cause.
- Background children that outlive the parent's turn and follow-up conversations with an existing child are not supported.
