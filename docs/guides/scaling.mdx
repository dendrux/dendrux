# Scaling workers

Dendrux is a library. You own the processes, the database pool, the migration job and the schedule. The database coordinates claims: any worker can resume any run, and Dendrux keeps no state that matters in process memory. This page lists what to build once, what to size, and which limits bound the work a process accepts.

## Build the store once at startup

Build the store when a worker starts and pass it to every `Agent` that worker serves. Constructing an `Agent` does no I/O and is cheap; the engine and its pool are not.

[//]: # "docs-test: skip - application lifecycle and an already migrated production database are required"

```python
from sqlalchemy.ext.asyncio import create_async_engine
from dendrux import Agent
from dendrux.store import PostgresStateStore
from dendrux.store import RunStore

engine = create_async_engine(
    "postgresql+asyncpg://user:password@database/app",
    pool_size=5,
    max_overflow=0,
    pool_timeout=10,
    pool_pre_ping=True,
    pool_recycle=1800,
)
state = PostgresStateStore(engine)
reads = RunStore(state)
agent = Agent(
    name="worker",
    prompt="Help the user.",
    provider="openai:gpt-4o-mini",
    state_store=state,
)
# Start application requests here, then drain them before shutdown.
await agent.close()
await reads.close()
await state.close()
await engine.dispose()
```

The store runs the agents (`PostgresStateStore` here; `MySQLStateStore` or `SQLiteStateStore` the same way, or `store_for_engine(engine)` to pick one from the engine); `RunStore(state)` supplies the read facade over the same store, and listens for live updates when the store has them (see [Live updates](#live-updates)). `RunStore.from_engine(engine)` is the polling-only alternative. Shut down in this order: agents, readers, the store, then the engine. `await state.close()` closes the store's live-update connections and never disposes your engine. You keep ownership of the engine and dispose it after all work and readers have stopped. Avoid holding a database session while you await an agent run, a tool or a browser.

Build the engine in the worker process, after any fork, on the event loop that will use it. Async Postgres pools belong to their creating loop; using one from another loop is refused with a clear error. Build one store per worker loop instead of calling `asyncio.run` per request. See also [Web endpoints](/docs/recipes/web-endpoint).

### What happens if you pass `database_url=` per request

An `Agent(database_url=...)` with the same normalised URL and the same `database_options` reuses one process-wide engine:

- Concurrent first callers share one initialisation. Each initialised Agent holds one reference.
- `Agent.close()` releases the reference; the engine is disposed when the last holder closes or the process exits. **Close every Agent**, including after failed requests (`async with Agent(...)` does this).
- Different options select different pools on purpose.
- Equal in-memory SQLite URLs share one database while the pool lives. Use a distinct engine or a temporary file when tests need isolation.
- A pool whose owning event loop has closed is retired lazily on the next matching acquisition or release. Orphaned connections are released by garbage collection, so they can linger until then and briefly exceed the new pool's limits. Each retirement logs one WARNING with `code=shared_engine_loop_closed`, without a URL or credentials. No timer or background task is involved: await `agent.close()` before you close the loop for prompt cleanup.
- At process exit pools are retired synchronously and the operating system closes the sockets.

This stops a per-message Agent from opening a new pool each time, but an explicit `state_store=` stays the recommended path: you choose the pool size and you see the lifecycle. The Agent ignores `DENDRUX_DATABASE_URL`. If it is set and no effective store is supplied, run and stream have no persistence and log `database_url_env_ignored` once per process, without raising just because the variable is set. A returned pause cannot be submitted later without persistence. Pass `state_store=` or `database_url=` explicitly; the CLI still uses the variable. A store created by `RunStore.from_database_url` owns its engine and must also be closed.

## Pool sizing per worker

Each worker process has its own pools. Add `pool_size + max_overflow` across every process, reader, maintenance job and other application, and keep the total under the database's connection limit with headroom for migrations and operations. Choose a finite `pool_timeout` so overload waits briefly and fails visibly instead of building an unlimited backlog. A smaller dedicated reader pool keeps viewer traffic from competing with running agents.

## Managed database idle timeouts

For non-SQLite URLs Dendrux defaults `pool_pre_ping` to `True` and `pool_recycle` to 1800 seconds. Pre-ping checks a connection at checkout and replaces a disconnected idle one; recycling replaces old connections at checkout. Pick a recycle interval shorter than your managed database's or proxy's idle cutoff. `database_options=` overrides either setting on `Agent`, `RunStore.from_database_url` and `sweep`.

Pre-ping cannot recover a transaction killed while it is executing. Dendrux retries persistence writes where that is safe; tools with external side effects still need their own idempotency. Apply database timeouts and monitor failures instead of retrying a whole run blindly. A database write that still fails after the retries makes `agent.run` raise `PersistenceError` (a stream ends with `run_error`), with a fixed message that carries no SQL, parameters or driver text; the run is saved as `error` if the database answers again in time, and otherwise stays `running` at its last committed state for `sweep` and `reclaim` to recover (see [Errors](/docs/reference/errors#when-a-write-fails-inside-a-run)). Engines Dendrux creates hide bound parameters. A Postgres statement timeout is never retried; the [retry rules](/docs/upgrading-to-0.6.0#database-retries) say exactly what is.

## PgBouncer in transaction mode

Disable both asyncpg statement caches when a transaction-mode pooler sits in front of the database. Keep runtime work transactional: Dendrux uses no session-level `SET`, session advisory lock, temporary table or `LISTEN` on the pooled path. The one advisory lock it takes, when it inserts an inbox note, is transaction-scoped and released with the transaction.

[//]: # "docs-test: skip - requires a configured external PgBouncer endpoint"

```python
options = dict(
    pool_size=5,
    max_overflow=0,
    connect_args=dict(
        statement_cache_size=0,
        prepared_statement_cache_size=0,
    ),
)
```

Pass these as `database_options=` (or as keyword arguments to `create_async_engine`). Migrations, activation and LISTEN need separate connections. The live-update sender works through a transaction pool because NOTIFY is transactional; the listener does not, so give `PostgresUpdates` a direct or session-pooled `listen_url` (see [Behind PgBouncer](#behind-pgbouncer)).

## Migrations: one job, direct connection

Run `dendrux db migrate` **once per deploy, as a single job**, over a **direct** Postgres connection (not through PgBouncer, and not from every pod at startup). Run it before starting the new workers. A second concurrent runner refuses with a retry message instead of racing.

- The migration uses session-level locks and `lock_timeout` settings, which is why it needs a direct session connection.
- Short exclusive steps wait at most 5 seconds for each lock and then fail with a retry message. Finish the long-running transaction that blocked it and run the job again. The index builds run concurrently and a timed-out build is repaired on the retry. The 5 second budget is fixed; schedule the job in a quiet window.
- The `status_changed_at` backfill is online, in 5,000-row commits, and works best on Postgres 12 or later. The concurrent index build on a large `run_events` table can take minutes.
- `dendrux db check` compares the database with this version's head without changing anything (exit 0 current, 1 behind, 2 unknown). A non-SQLite database that was not migrated fails at startup with `SchemaOutOfDateError`.
- Do not start abandoned-waiting sweeps until the migration has finished.

For 0.6, migration is additive and leaves format 1 enabled. Roll every worker and read-only consumer, take a pre-activation backup, then run `dendrux db activate` over a direct connection. Only then enable reclaim and live updates. Activation is one-way. See [Upgrading to 0.6.0](/docs/upgrading-to-0.6.0) and the [Database CLI](/docs/reference/cli).

## MySQL and MariaDB

The same rules apply: one store per worker, bounded pools and one migration job. The differences are in [MySQL and MariaDB](/docs/guides/mysql): engines need `READ COMMITTED` and a UTC connection (engines Dendrux creates set both), `dendrux db migrate` is forward-only and holds a server-wide named lock, the Agent's `Limits` are compared with the server's `max_allowed_packet` before first use, and live updates have no built-in MySQL transport, so `follow` polls unless you give the store a `RedisUpdates` or your own bus (see [Redis](#redis)).

## Sweep cadence

`sweep()` finds stale `running` rows and abandoned waiting rows. Call it from your own maintenance job, at startup and at an interval that suits the application; Dendrux never schedules it.

- Set `stale_running` at least three times `Agent.lease_interval` (default 30 seconds, minimum 5 seconds), with room for database latency and event-loop stalls. Lease renewals run while a model or tool call is in flight; they stop when that call scope closes. A tool can also call `heartbeat()` to report progress. Progress writes only touch `running` rows under the current epoch.
- Choose `on_stale="error"` to finalize stale runs, or `"reclaim"` to mark eligible format-2 ReAct runs for your own dispatcher. Omission retains error finalization in 0.6 and warns when stale rows are found. Dendrux never dispatches marked runs itself.
- `max_runs` (default 10,000, ceiling 100,000) bounds how many candidates one call inspects **per category**, and `batch_size` (default 100, ceiling 1,000) sets the page size. Fresh `running` rows and compare-and-swap attempts that lose a race count against the bound. `max_returned` (default 1,000, ceiling 100,000) bounds returned reclaimable items. Continue the running scan with `SweepResult.cursor` until it is `None`; a scan never wraps. Repeat from the beginning on a later sweep. Waiting scans have no cursor; repeat calls to drain them. A short result does not prove the backlog is empty.
- A waiting run is abandoned only when **both** its last status change (`status_changed_at`) and `updated_at` are older than `abandoned_waiting`. The second check protects pauses written by 0.4.1 workers during a rolling deploy; a recent metadata edit delays abandonment by one window.
- Swept waiting rows get the safe error `Run swept as abandoned_waiting` together with `failure_reason`.
- Candidate scans use indexes on status and transition time. Heartbeat timestamps are not indexed, so progress writes stay eligible for Postgres HOT updates.

See [Recovery](/docs/guides/recovery) for attempt limits, recovery approval and bounded dispatch.

## Live updates

Live updates tell other processes that a run may have changed, so `follow()` and `stream_events()` read it as soon as the hint arrives instead of waiting for the next poll. They are optional and off by default.

> **Hints are lossy; the database is the truth.** A hint carries only run ids. It can arrive late, twice, out of order or never, and a reader always re-reads the database before it shows anything. An announcement never fails, rolls back or changes the result of a save. If every hint is lost, followers still see every event: they poll.

### Turn them on

Live updates are configuration of the **store**, not of the `Agent` or the `RunStore`:

| `live_updates=` | Meaning |
| --- | --- |
| `None` or `False` (default) | Off. The store announces nothing and followers poll. |
| `True` | The store's built-in transport. Only `PostgresStateStore` has one (`PostgresUpdates`). Any other store raises `ValueError` that names the store and suggests `RedisUpdates`. |
| a `LiveUpdates` instance | Used as given: `PostgresUpdates(...)`, `RedisUpdates(...)` or your own. An instance belongs to one store; binding it to a second store raises `ValueError`. |

Every `SQLStateStore` constructor takes it (`PostgresStateStore`, `MySQLStateStore`, `SQLiteStateStore`, `store_for_engine`), and `MySQLStateStore.from_url(url, live_updates=...)` takes it as a named argument.

[//]: # "docs-test: skip - application supplies its shared engine and Postgres deployment"

```python
from dendrux import Agent
from dendrux.store import PostgresStateStore, RunStore

state = PostgresStateStore(engine, live_updates=True)   # announces after each commit
reads = RunStore(state)                                  # listens for those announcements
agent = Agent(provider="openai:gpt-4o-mini", prompt="Help the user.", state_store=state)

async with reads.follow(run_id, tenant_id=tenant) as follow:
    async for event in follow:
        await send(event)

# At shutdown, in this order:
await agent.close()
await reads.close()    # releases this reader's listener; never closes the store
await state.close()    # closes the live-update connections; the engine stays yours
await engine.dispose()
```

What this does and does not do:

- **Only `RunStore(store)` listens.** `RunStore.from_engine(engine)` and `RunStore.from_database_url(url)` build stores without live updates, so their followers keep polling. A reader in another process builds its own store with live updates and wraps it the same way. Several `RunStore` objects over one store each take a listener lease; the listener runs until the last one closes.
- **Writers and readers need the same bus.** Every process that writes runs gives its store the same transport and channel as the readers. A writer without live updates is still correct: its runs are found by the safety poll.
- **`Agent(database_url=...)` cannot enable them.** `live_updates` and `notify_channel` keys are refused with a `ValueError` in `database_options` on `Agent`, `sweep(database_url=...)`, `get_engine` and `RunStore.from_database_url`, even when their value is `None` or `False`. Build the store yourself and pass it to `Agent(state_store=...)`, `sweep(state_store=...)` or `RunStore(store)`. `sweep(database_url=...)` uses a temporary store with no live updates.
- **There is no `notify_channel` option and no `listen_url=` on `RunStore`.** The channel and the listen URL belong to the transport: `PostgresUpdates(channel=..., listen_url=...)`.
- **A closed `Agent` closes only what it created.** `Agent.close()` closes the store it built from `database_url=`; a store you passed in is yours to close with `await store.close()`.

### What announces

A write announces the run ids it changed after its transaction's COMMIT was issued. These calls announce: creating a run; saving an event; starting and completing a tool call; finishing, pausing, claiming, releasing and reclaiming a run; submitting a pause decision; cancel and pause requests; metadata updates; lease marking; and the stale and abandoned sweeps. A write that fails before COMMIT, or whose COMMIT is proved not to have applied, announces nothing.

These writes are **polling-only** and announce nothing: `save_trace`, `save_tool_call`, `save_usage`, `save_llm_interaction`, `checkpoint_step`, `set_trace_link`, `add_note`, `mark_notes_delivered`, `touch_progress` and the blob-catalog writes. Their data is readable at once; a live view shows live usage totals and similar details at its next poll.

The announcement goes out when the outermost store call returns, after its database sessions are closed and outside the store's session lock. If the call raises, including `StoreOutcomeUnknown`, its ids wait for the next successful call on that store or for `close()`. A sweep flushes between pages, and flushes the earlier successes of a page that fails or is cancelled, waiting at most `flush_deadline_s` before it re-raises the original error. Hints still pending are only a delay: polling covers them.

### What a reader does

One coordinator task per `RunStore` and event loop serves every `follow()` on it. It reads all watched runs in chunks of up to 200 runs and 2,000 rows (one events query and one status query per chunk), spends at most 20 queries a second, and reads the run that has waited longest first. A hint never adds a run; it only makes a run you already follow due now.

| Situation | When the run is read |
| --- | --- |
| A hint arrives, or a follower joins | At once (events and status) |
| Live updates healthy, nothing arrives | Every `poll_healthy_s`, **10 seconds by default with 20 % jitter either way** (the safety poll) |
| Live updates off, or the listener is down | After `poll_interval_s` (0.5 s), backing off to `poll_max_s` (2 s) while idle; status on every fourth read |
| The listener reconnects, or incoming hints overflowed (a gap) | Every watched run once, spread by up to `poll_interval_s` of jitter |
| Any case | Status at most 30 seconds old; a full page of events is read again at once; a terminal run is drained until a page comes back empty before `FollowEnd` |

`stream_events` keeps its own per-caller polling and is woken by hints; prefer `follow`. If the live-update listener cannot start, readers poll and retry the listener after 30 seconds. Alert on the codes in [What to alert on](/docs/recipes/observability#what-to-alert-on).

### Postgres

`live_updates=True` builds `PostgresUpdates()`. It uses two dedicated asyncpg connections that never come from your pool: a **sender** (opened on the first announcement, one `pg_notify` statement per send, which can carry many ids) and a **listener** (opened when a reader on the store starts following). A process that writes adds one connection; a reader on the same store adds one more while it follows runs.

[//]: # "docs-test: skip - needs a PostgreSQL server"

```python
from dendrux.store import PostgresStateStore, PostgresUpdates

updates = PostgresUpdates(
    url=None,                      # default: the store's engine URL
    listen_url=None,               # default: the same URL as the sender
    connect_args=None,             # asyncpg options, for example {"ssl": ssl_context}
    channel="dendrux_events",
)
state = PostgresStateStore(engine, live_updates=updates)
```

- **The URL.** The transport uses the store's engine URL unless you pass `url=`; a custom store without a SQLAlchemy engine must pass it. SQLAlchemy's URL is converted to an asyncpg DSN with the same user, password, host, port and database, escaped. Only keys asyncpg itself reads are kept (`sslmode`, `sslrootcert`, `target_session_attrs`, `application_name`, `options` and the other connection keys). A SQLAlchemy-only key such as `?ssl=require` or `?prepared_statement_cache_size=0` is **refused** with a `ValueError` that names only the key: Dendrux never drops an option silently, because dropping `ssl` could change where and how it connects. This also applies to `live_updates=True` when the engine URL carries such a key, because the transport then uses the engine URL. The way out is to give the transport its own URL, `PostgresUpdates(url="postgresql+asyncpg://...?sslmode=require")`, or to keep the URL as it is and pass TLS settings in `connect_args={"ssl": ssl_context}`.
- **Fixed options.** `statement_cache_size=0` and the connection timeout are set by Dendrux; `connect_args` may not set `statement_cache_size` or `timeout`. The connections are named `dendrux-live-updates` unless you set an application name.
- **TLS.** The `connect_args` of your engine cannot be read back from SQLAlchemy. For a remote host with neither `sslmode` in the URL nor `ssl` in `connect_args`, Dendrux logs `live_updates_tls_unknown` once. Set one of them explicitly.
- **Payload.** Postgres rejects a notification of 8,000 bytes or more, so `max_message_bytes` must be at most 7,999 (the default is 7,900).
- **Primary only.** NOTIFY reaches listeners on the same server. A read replica never receives the notifications of its primary; point the sender and the listener at the primary.

### Behind PgBouncer

NOTIFY is transactional and works through a transaction-mode pooler. LISTEN needs a session and does not. Keep `url` (or the engine URL) on the pooler and give the listener a direct or session-pooled endpoint of the primary:

[//]: # "docs-test: skip - requires a configured external PgBouncer endpoint and a direct primary endpoint"

```python
from dendrux.store import PostgresStateStore, PostgresUpdates

updates = PostgresUpdates(listen_url=direct_primary_url)
state = PostgresStateStore(engine, live_updates=updates)
```

Never point `listen_url` at a transaction pool.

### Redis

Any store can announce over Redis Pub/Sub. This moves the hints off the database server; it does not remove the fan-out, because Redis also delivers every message to every subscriber. Install the optional extra (it is not part of `dendrux[all]`):

```bash
pip install "dendrux[redis]"
```

[//]: # "docs-test: skip - needs a running Redis server"

```python
from dendrux.store import MySQLStateStore, RedisUpdates, RunStore

updates = RedisUpdates(
    "rediss://redis.internal:6379/0",
    channel="myapp:prod:dendrux",      # unique per application and environment
    client_options=None,               # extra redis-py options, for example {"ssl_cert_reqs": "required"}
)
state = MySQLStateStore(engine, live_updates=updates)
reads = RunStore(state)
```

- **Importing needs nothing; constructing needs the extra.** `from dendrux.store import RedisUpdates` works without the Redis client. Calling `RedisUpdates(...)` without it raises `ImportError` that names `pip install dendrux[redis]`. The client is `redis>=5.0.1,<9`. Releases 5.0.1, 5.3.1, 6.4.0, 7.4.0 and 8.1.0 are tested; another release in the range is checked when you construct the transport and refused with `ImportError` if its parser cannot bound a message.
- **Name the channel.** Pub/Sub ignores the Redis database number, so the default `dendrux:events` is a starting point, not a namespace. Use one channel per application and environment, and the same one on every writer and reader.
- **URLs.** `redis://`, `rediss://` (TLS) and `unix://`. A URL query string or `client_options` that sets the timeouts, retries, connection pool, `protocol`, `parser_class`, `host`, `port` or a second connection is refused with a `ValueError`, because Dendrux fixes those. A text `encoding` other than UTF-8 is refused too.
- **Connections.** The sender is one connection used for one pipelined round trip per send. The listener is one Pub/Sub connection on the pure-Python RESP2 parser (hiredis is not used for it), so an oversized message is refused before it is read. It never reconnects silently: a lost connection is reported as a gap and the transport reconnects with backoff.
- **Liveness.** The listener sends a token-matched `PING` on its own connection after `health_check_s` (15 s) of silence and finds a dead connection within twice that time.
- **Secrets.** The URL, host and password never appear in logs, errors or `repr`. Hints carry run ids only, but the channel is as trusted as the Redis server: use ACLs and `rediss://`.

### Write your own bus

A `LiveUpdates` subclass needs two methods; the base class owns batching, de-duplication, deadlines, backoff, the wire format, health, reconnects and shutdown.

| Method | Contract |
| --- | --- |
| `async send(self, messages)` | Deliver the encoded messages in **one** transport round trip, including any connection setup (that counts against the flush deadline). Raise on failure. Cooperate with cancellation. |
| `receive(self)` | An async iterator. Connect and subscribe, yield `None` **once, after the server confirmed the subscription** (within `4 * send_timeout_s`), then yield each raw message string. End or raise when the connection is lost, and detect a dead connection yourself, on the same connection you listen on, within `2 * health_check_s`. Hold at most `max_inbound` undelivered messages; when you drop the oldest, yield `LiveUpdates.GAP` (the exact object) so readers re-read. Close your listen connection in a `finally`. |
| `bind(self, store)` (optional) | Learn what you need from the store, for example its engine URL. Called once, when the store takes the instance. |
| `abort_sender(self)` (optional) | Synchronously drop the send connection now. Called after a failed or cancelled send; must be quick and safe to call twice. |
| `abort_listener(self)` (optional) | Synchronously drop the listen connection when a forced shutdown gives up waiting. |
| `async aclose_sender(self)` (optional) | Close the send connection at `close()`. |

You never parse messages. On the wire a message is a compact JSON array of run-id strings of at most `max_message_bytes` UTF-8 bytes, built and read by the base class; a message that does not decode to a list of non-empty strings within the limits is dropped whole and counted. A batch of ids is split into as many messages as it needs and handed to one `send` call.

This runnable example is a loopback bus that delivers hints inside one process. Replace the queue with NATS, Kafka, a socket or whatever your platform provides:

```python
import asyncio
from collections.abc import AsyncIterator, Sequence

from dendrux import Agent
from dendrux.db.session import get_engine
from dendrux.store import LiveUpdates, RunStore, SQLiteStateStore


class LoopbackUpdates(LiveUpdates):
    """Delivers hints inside one process. A real bus does the same over a network."""

    def __init__(self, **limits) -> None:
        super().__init__(**limits)
        self._queue: asyncio.Queue[str] = asyncio.Queue()

    async def send(self, messages: Sequence[str]) -> None:
        for message in messages:
            self._queue.put_nowait(message)

    async def receive(self) -> AsyncIterator[str | None]:
        yield None  # the subscription is live
        while True:
            yield await self._queue.get()


engine = await get_engine("sqlite+aiosqlite:///live-updates.db")
bus = LoopbackUpdates()
state = SQLiteStateStore(engine, live_updates=bus)
reads = RunStore(state)
agent = Agent(
    provider="anthropic:claude-haiku-4-5",
    prompt="Reply briefly.",
    state_store=state,
    strict_tenancy=False,  # single-tenant example
)
result = await agent.run("Hello")
assert bus.stats().sent > 0  # the run announced itself
await agent.close()
await reads.close()
await state.close()
```

Limits are keyword arguments of the base constructor, shared by every transport:

| Limit | Default | What it bounds |
| --- | --- | --- |
| `max_pending` | 10,000 | Ids waiting to be sent. Over the bound the oldest are dropped (counted, logged once as `live_updates_overflow`) |
| `max_batch` | 500 | Ids per `send` call |
| `max_message_bytes` | 7,900 | UTF-8 bytes per message |
| `max_run_id_len` | 255 | Longer ids are dropped when enqueued |
| `send_timeout_s` | 0.5 | One `send` call |
| `flush_deadline_s` | 1.0 | One whole flush, connection setup included |
| `close_timeout_s` | 3.0 | Everything `close()` does |
| `max_inbound` | 1,000 | Received messages not yet handled; overflow is a gap |
| `backoff_initial_s`, `backoff_max_s` | 0.5, 30.0 | Pause after a failed send, doubling; also the listener's reconnect delay, with full jitter |
| `health_check_s` | 15.0 | Silence before a transport probes its listen connection |

A custom store that is not built on `SQLStateStore` can use the same instance; see [Build your own store](/docs/guides/build-your-own-store#live-updates-in-a-custom-store).

### Costs, bounds and failure behaviour

- **A save pays for one announcement round trip**, on the separate sender connection, after its transaction. If the bus stalls, a save waits at most `flush_deadline_s` (1 second), the failed batch is dropped, sending pauses (0.5 seconds, doubling to 30) and further saves pay nothing until it resumes. A store call that fails never waits for an announcement.
- **At close**, the store sends one last flush, within `flush_deadline_s` and inside the `close_timeout_s` budget for everything `close()` does. If the sender is in backoff, that final flush is skipped and the pending ids are dropped and counted; readers recover them by polling. `close()` is idempotent and safe to call from several tasks.
- **One event loop per instance.** An instance belongs to the first event loop that uses it. Enqueueing from another loop is dropped and counted (logged once as `live_updates_wrong_loop`), so a save never fails because of it, and `close()` or a listener lease from another loop is refused with `RuntimeError`. Build one store per worker loop.
- **Many open stores.** Each store with live updates holds its own sender connection. When more than 16 stores announce to one database in a process, Dendrux warns once (`RuntimeWarning` and `live_updates_many_stores`). Share one store per database and close the ones you no longer use.
- **Counters.** `store.live_updates.stats()` returns a `LiveUpdatesStats` (pending count, `oldest_pending_age_s`, ids sent, drops by cause, gaps), and `.healthy` says whether the listener holds a live subscription. `oldest_pending_age_s` is how long a stranded hint has waited.
- **Stranded hints.** There is no sender task. Ids enqueued while another flush runs, after a flush hit its deadline, or during backoff wait for the next flush or for `close()`, and may be lost. That is by design: followers find them by polling.
- **Cost of NOTIFY on Postgres.** Postgres takes a database-wide lock at the commit of every transaction that sent a NOTIFY. In 0.6 that transaction is the sender's own short statement, not your save, and one statement carries a whole batch of ids, so a busy writer pays the lock once per batch of up to 500 ids rather than once per saved event. Measure your own event rate and write workload before relying on a capacity figure.
- **A stuck Postgres listener can fill the notification queue.** Monitor `pg_notification_queue_usage()` and investigate sustained growth. A full queue now fails the announcement, which the store absorbs, instead of failing the save. Every listener process receives **every notification on its channel**, including run ids it does not watch, so bus load is readers times notifications on Postgres and Redis alike. Payloads contain run ids only.

## Live readers and bounded work

Every queue Dendrux keeps has a default and an override. Size these with your worker count:

| Resource | Default | Over the bound | Override |
| --- | --- | --- | --- |
| Live `follow` readers per store (process) | 500 | `FollowCapacityError`, answer 503 | `EventFeed(store, max_followers=...)` |
| Live `follow` readers per tenant scope | 100 (a fifth of the store cap) | `FollowCapacityError(per_tenant=True)` | `EventFeed(store, max_followers_per_tenant=...)`, or `None` to turn it off |
| One `follow` reader | 900 s | ends with `FollowEnd("max_duration", cursor)` | `max_duration_s=` |
| Sync tool threads per process | 32 | calls queue | `DENDRUX_TOOL_THREADS` |
| Sync tool threads per Agent | 8 | calls queue | `Agent(tool_threads=...)` |
| Tool calls waiting per Agent | 256 | retryable `tool_pool_saturated` result, the tool never starts | `DENDRUX_TOOL_QUEUE_LIMIT` |
| MCP discovery | 100 pages, 2,000 tools, 60 s, 16 MiB (HTTP) | `MCPDiscoveryLimitError` | `MCPSource` options |
| `sweep` candidates per category | 10,000 (ceiling 100,000) | `sweep_cap_reached` warning | `max_runs=` |
| `list_runs` offset | 10,000 | `ValueError` | none |
| Tool calls queued per process | 1,024 | retryable `tool_pool_saturated` result | none |
| `sweep` page size | 100 (ceiling 1,000) | `ValueError` | `batch_size=` |
| `sweep` returned reclaimable runs | 1,000 (ceiling 100,000) | result is capped | `max_returned=` |
| `sweep` reclaim attempts | 3 (ceiling 32,767) | run stops being reclaimable | `max_reclaims=` |

| Lease renewal deadline | half the interval, at most 10 s | renewal counts as failed | none |
| Consecutive lease failures | 2 | owner stops after lease loss | none |
| Agent iterations | 10 (ceiling 200) | run stops at configured limit | `Agent(max_iterations=...)` |
| Provider response / stream bytes | 16 MiB / 16 MiB | `ProviderResponseError` | provider `max_response_bytes=` / `max_stream_bytes=` |
| Provider stream tool calls | 1,000 | `ProviderResponseError` | provider `max_stream_tool_calls=` |
| Provider output tokens / SDK retries | 16,000 / 3 | provider output / retry bound | provider `max_tokens=` or `max_output_tokens=` / `max_retries=` |

The follower cap is per **scope**, not per user. A string `tenant_id` is one scope, all untenanted (`None`) followers are one scope, and all `UNSCOPED` followers are one scope. A single-tenant app with more than 100 live readers per process builds its own feed with `max_followers_per_tenant=None`; see [Build your own read routes](/docs/recipes/build-your-own-read-routes).

The coordinator described under [What a reader does](#what-a-reader-does) serves every follower of a `RunStore`, so database load grows with watched runs, not with open connections. A follower costs a small constant number of statements however many pauses the run has, and `get_pending` is bounded whatever the size of the stored pause: one projected read for a client-tool or requested pause, three bounded reads (summary, active-pause sequence, recorded model arguments) for an approval or input pause. Attaching the pending pause to a result adds one projected read for a client-tool or requested pause and three for an approval or input pause, once per pause; `Agent.get_result` adds three reads, or five for an approval or input pause.

Event numbering is allocated inside the insert statement, so a writer never reads the event log first. Notes are capped by one conditional insert, so concurrent `submit_note` calls cannot exceed `max_notes_per_run`.

## Read replicas

Read replicas are your deployment choice. Keep claims, tool submissions, cancellation, migrations and sweeps on the writer. Replica lag can delay pending state and event visibility, so a UI must not treat a replica's stale pause as authority to submit a decision. Submissions validate the current pause id on the writer through `expected_pause_id`. Choose where authorized reads and follow polling run, how lag is monitored, and when the app routes a read back to the writer.

## History storage grows with replay

Every run is stored in full, and a run that replays earlier runs stores what it replayed again. With `runs=` on a format-2 store, the replayed messages are written as seed rows (`react_traces`) of the new run, so the rows each new run writes grow with the number of runs you replay, and each model call stores its full request in `llm_interactions`. Nothing is deduplicated in 0.6, so a long replayed conversation costs storage in proportion to how much it replays, even when each turn's own tool result is small.

`replay_last` limits how many of the most recent runs replay in full (text, tool calls and results); older runs replay as question and answer only. A window lowers the growth a lot, but it does not stop it: older question-and-answer pairs still replay and are stored again.

One synthetic probe shows the shape. It ran 50 turns on SQLite with a fake model, one tool call and one 4,400-character result per turn, passing every earlier run in `runs=`. The figure is the sum of the stored column values, not the database file: it leaves out indexes, page overhead and the WAL.

| Replay setting | After turn 1 | After turn 10 | After turn 50 |
| --- | --- | --- | --- |
| `replay_last="all"` | 22,894 bytes | 996,794 bytes | 22,005,246 bytes |
| `replay_last=1` | 22,894 bytes | 419,949 bytes | 3,162,681 bytes |

This is one workload with a fake model, not a capacity guarantee; real conversations differ in length, tool results and history. What to do about it:

- Pass `runs=` only for the runs a turn needs, and choose a window (`replay_last=N`) for long threads. See [Memory across runs](/docs/recipes/run-replay).
- Size the database for the replay setting you use, and measure with your own conversations.
- Keep large tool results out of the model's context where you can; every result replayed in full is stored again.

## Load testing your deployment

The repository includes a monitored load harness, `tools/load.py`. It builds a private database, runs fake-provider agents across several processes, and records statements per run, timings and resource samples (process memory, descriptors, tasks, pool use and, where the platform allows, database and container counters). It repeats each workload for four cycles and fails if memory, descriptors, tasks or connections keep growing between cycles. Run it on a quiet machine from `packages/python`, with the development dependencies installed.

The harness drops and recreates the tables of the database you give it, so it accepts only private databases whose name ends in `_test`. For MySQL and MariaDB the name must also contain `_load_`, the host must be loopback and the port 53306 or 53307 (the repository's test servers), unless you opt in to another port with `--allow-port`.

```bash
# Postgres: the 1,000-run scenario on a private database ending in _test
export DENDRUX_LOAD_PG_URL=postgresql+asyncpg://user:password@localhost:5432/dendrux_load_test
make load-pg

# MySQL and MariaDB: run from packages/python in a repository checkout. Start the test servers
# first; the ceilings are in tools/load_budgets_mysql.json
make test-dbs-up
make load-mysql
make load-mariadb
```

`make load-quick` runs every scenario at small scale and fails on a statement-count regression against `tools/load_baseline.json` (Postgres only); `make load` is the full run. MySQL and MariaDB have no stored baseline, so the ceilings are declared before measuring: `tools/load_budgets_mysql.json` maps each gate to a number (`runs.statements_per_run` is 50; the 0.6 runs measured about 47). The targets use it by default; pass `LOAD_STATEMENT_BUDGETS=path` to use your own file. Results are written as JSON to `LOAD_JSON` (default: `dendrux-load-results.json` in your temporary directory) with a compact Markdown table. Workloads that need the Postgres live-update transport (the `notify` scenarios) are skipped on MySQL and MariaDB, with a note.
