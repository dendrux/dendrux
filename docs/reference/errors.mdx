# Errors

Dendrux's runtime methods raise typed exceptions on precondition failures. You catch them in your own routes (or CLI, or jobs) and map them to status codes. Dendrux never forces a status-code contract.

```python
from dendrux.errors import (
    RunNotFoundError, RunNotPausedError, PauseStatusMismatchError,
    RunAlreadyClaimedError, RunAlreadyTerminalError, InvalidToolResultError,
    PersistenceNotConfiguredError, SchemaNotInitializedError, SchemaOutOfDateError,
    SkillValidationError, SkillMissingError, SkillMismatchError,
    ContextLengthExceededError,
    ImageError, InvalidImageError, ImageLimitError, ImageFetchError, UnsupportedModalityError,
    ImageRejectedError, ProviderError, BlobNotFoundError, BlobIntegrityError,
    ImagePersistenceUnsupportedError, BlobContentionError,
    ProviderAuthError, ProviderRateLimitError, ProviderTimeoutError, ProviderUnavailableError,
    ProviderStreamIncompleteError, ModelRefusalError, ContentFilteredError,
    BudgetConfigurationError, TenantScopeRequiredError, GovernanceMismatchError,
    NoteLimitExceededError, PersistenceError, StoreOutcomeUnknown, StatementTooLargeError,
    JSONIntegerOutOfRangeError, RunControlError,
    RunNotReclaimableError, RunCancelledError, StoreCapabilityError, LiveUpdatesUnavailableError,
    SubtreeTooLargeError,
)
from dendrux.types import InputValidationError   # also a ValueError
from dendrux.store import FollowCapacityError
```

The most common ones are also re-exported from the top-level `dendrux` package.

## The hierarchy

`RunNotPausedError`, `PauseStatusMismatchError`, `RunAlreadyClaimedError` and `RunAlreadyTerminalError` now share `RunControlError`, which still subclasses `RuntimeError`. Existing catches continue to work.

| Exception | Base | Raised when | Suggested HTTP |
| --- | --- | --- | --- |
| `RunControlError()` | `RuntimeError` | Shared base for run-control conflicts. Catch a more specific class when choosing a recovery action. | per subclass |
| `RunNotReclaimableError(run_id, reason)` | `RunControlError` | Recovery preconditions fail, a mark was already claimed, or history reconstruction is refused. `RunStore.get_traces` on a format-2 run raises it with `reason="history_too_large"` when the conversation is above 20,000 expanded rows or 16 MiB; see [Bounded list reads](/docs/reference/run-store#bounded-list-reads). `reason` is a stable code. See [Recovery](/docs/guides/recovery). | 409 |
| `RunCancelledError(run_id, parent_run_id)` | `RunControlError` | Delegated-child creation finds a terminal parent or a pending parent cancellation. | 409 |
| `StoreCapabilityError(store, capability, method, missing)` | `TypeError` | A declared store capability has an incompatible method or keyword signature, or its `version` or `deployment` is wrong. The message names the capability, the method and the missing parameters and gives the repair; see [Fixing a `StoreCapabilityError`](/docs/reference/state-store#fixing-a-storecapabilityerror). Fix the store before accepting work. | 500 |
| `LiveUpdatesUnavailableError(reason)` | `RuntimeError` | `RunStore` cannot take its internal listener lease: the instance is closed, or an earlier listener did not stop within its deadline. `reason` is `timeout`, `connection`, `cancelled`, `closed` or `other`. Taking a lease starts the listener task at once; connection or subscription failures then degrade and retry inside that task, so check `updates.healthy` to know whether the subscription is live. Taking a lease from another event loop raises `RuntimeError`, a separate error. `RunStore` readers catch both, poll, and ask again after 30 seconds, so you rarely see either. | 503 |
| `RunNotFoundError(run_id)` | `LookupError` | `run_id` does not exist, or belongs to a tenant other than the one you passed. The same error for both, from `Agent`, `retry` and `RunStore` alike (`dendrux.store.RunNotFoundError` is an alias of this class). | 404 |
| `RunNotPausedError(run_id, current_status)` | `RuntimeError` | A submit method is called on a run that is not paused. | 409 |
| `PauseStatusMismatchError(run_id, current_status, expected_status, *, expected_pause_id=, current_pause_id=, reason=)` | `RuntimeError` | `reason="status"` (the default): a submit for the wrong pause type (e.g. `submit_tool_results` on `waiting_human_input`). `reason="pause_id"`: the call carried an `expected_pause_id=` that is no longer the run's current pause, so it is a stale submit; nothing was claimed or written. See [Pause ids and stale submits](/docs/architecture/pause-resume#pause-ids-and-stale-submits). | 409 |
| `RunAlreadyClaimedError(run_id)` | `RuntimeError` | A concurrent submit already won the CAS claim on this pause. | 409 |
| `RunAlreadyTerminalError(run_id, current_status)` | `RuntimeError` | A submit method, or `submit_note`, targets a run that is already terminal; also a submit on a run whose cancellation was requested but not yet observed. (`cancel_run` and `request_pause` do not raise this.) | 409 |
| `InvalidToolResultError(run_id, detail)` | `ValueError` | Submitted tool results do not match the pending set: an unknown, duplicate or missing call id, a tool name that differs from the pending call, a payload that is not valid, finite JSON or text, or an approval-path result that is not a failed denial. `detail` is a fixed description and never echoes a client id or payload. The run stays paused and unclaimed. | 400 |
| `InputValidationError(field, code)` | `ValueError` | A client value cannot be accepted or stored: `field` names a fixed API field (never an input key or value) and `code` is `invalid_identifier`, `invalid_text` (NUL or a lone surrogate), `invalid_json`, `nonfinite_json`, `structure_limit` or `pause_id_required` (a pause with a stored id continued without `expected_pause_id` when approving or under strict tenancy). These input checks run before writing or claiming. History reconstruction can also raise `InputValidationError(field="history", code="history_too_large")` after a submitted continuation claims the run. That postclaim failure releases the claim and restores the waiting status. Import it from `dendrux.types`. | 400 |
| `PersistenceError()` | `RuntimeError` | A database operation failed. SQL, bound parameters and driver text are omitted (`safe_message`, `retryable`). A write that fails after the retries makes `agent.run` raise it and `agent.stream` end with `run_error`; see [When a write fails inside a run](#when-a-write-fails-inside-a-run). | 500 or 503 |
| `StoreOutcomeUnknown()` | `PersistenceError` | A connection failed during `COMMIT` and the store cannot prove whether the write happened. `code` is `store_outcome_unknown`. Claims and reclaims always raise it after an ambiguous commit: do not run the claimed work, do not retry the claim, and do not read a later epoch as proof of ownership. The lease and `reclaim` recover the run. Writes that carry a retry identity are read back and report their true outcome instead. A blind retry of the same submit call gets `RunNotPausedError` when the first attempt did land. See [When a commit acknowledgement is lost](#when-a-commit-acknowledgement-is-lost). | 503 |
| `StatementTooLargeError(limit=None, size=None)` | `PersistenceError` | MySQL or MariaDB answered a statement with its packet-too-large error (1153, or 1301 for an oversized function result). `code` is `statement_too_large`; `limit` is the server's `max_allowed_packet` in bytes when known; `size` is best effort and usually `None`; no value is in the message. Not retried, nothing persisted. Servers usually close the connection instead of answering: when a MySQL-family connection is lost and a value bound to the failed statement is larger than the store's `max_allowed_packet`, the store raises this error after one attempt. A lost connection with no oversized value is an ordinary transient failure. Shrink the payload or raise the server limit. See [MySQL and MariaDB](/docs/guides/mysql#payload-limits-and-max_allowed_packet). | 413 or 500 |
| `JSONIntegerOutOfRangeError()` | `PersistenceError` | The MySQL store refused a JSON integer outside signed int64 / unsigned uint64 (-9223372036854775808 through 18446744073709551615), because MySQL would store it as an approximate decimal. `code` is `json_integer_out_of_range`; not retryable; nothing is written. The range applies to each JSON field you write (input, metadata, tool results, patches) on its own. Send larger integers as strings. MariaDB, PostgreSQL and SQLite keep large integers exactly and do not raise it. | 400 or 500 |
| `SubtreeTooLargeError(run_id, max_nodes)` | `ValueError` | `RunStore.get_subtree(..., max_nodes=N)` found that the descendants of the root (the root itself is not counted) reached `N`. Nothing is returned. It carries `run_id` and `max_nodes`, and logs `subtree_limit` with `run_id` and `limit`. It bounds the node count, not memory. Catch it to report the refusal, or retry with a larger bound you chose. See [`get_subtree`](/docs/reference/run-store#get_subtree). | 422 |
| `FollowCapacityError(limit, per_tenant=False)` | `RuntimeError` | `RunStore.follow` has no free follower slot: the store cap, or (`per_tenant=True`) the cap for that tenant scope. Safe to retry shortly. See [Build your own read routes](/docs/recipes/build-your-own-read-routes). | 503 |
| `PersistenceNotConfiguredError()` | `RuntimeError` | A method needs persistence but no `database_url` / `state_store` is configured (the Agent ignores `DENDRUX_DATABASE_URL`; without a store its presence logs `database_url_env_ignored` once per process). | 500 |
| `SchemaNotInitializedError()` | `RuntimeError` | The database has no Dendrux tables yet (non-SQLite needs `dendrux db migrate`). Also raised from any failing statement that names a missing table (MySQL 1146, PostgreSQL 42P01, SQLite "no such table"), on every store path including an engine you own, with the `dendrux db migrate` hint and no driver text. The tuples may be empty then, because the error comes from the statement, not from a catalog inventory. | 500 |
| `SchemaOutOfDateError(missing_tables=(), missing_columns=(), missing_indexes=())` | `RuntimeError` | A non-SQLite database is missing tables, columns or required indexes this version needs, because `dendrux db migrate` was not run after upgrading. Raised once per engine, before the first run (`Agent`, `sweep`; `RunStore` is not checked). Table/column presence and required Postgres index definitions/readiness are verified; column types and defaults are not. Carries `err.missing_tables`, `err.missing_columns` (`"table.column"`), `err.missing_indexes` and `err.missing`. A failing statement that names a missing column (MySQL 1054, PostgreSQL 42703, SQLite "no such column") raises it too, on every store path, with empty tuples. `DENDRUX_SKIP_SCHEMA_CHECK=1` skips the catalog check only; it does not turn off this classification. See [Upgrading](/docs/architecture/state-persistence#upgrading). | 500 |
| `ContextLengthExceededError(message, status_code=, provider_code=, model=)` | `ProviderError` | A provider rejected a batch or streaming request as larger than the model's context window. The SDK error is chained as `__cause__`; the message never contains prompt content. See [Models and providers](/docs/architecture/models#request-errors-on-openai-compatible-endpoints). | 413 or 400 |
| `ProviderError(provider=, model=, status_code=, provider_code=, category=, retryable=, timeout_reason=)` | `RuntimeError` | The base of every failed LLM request in 0.5.0. Carries `.category`, `.retryable` and `.safe_message`; the SDK exception is on `__cause__`. See [Provider errors](#provider-errors). | 502 |
| `BudgetConfigurationError(model=, reason=)` | `ValueError` | `Budget(max_cost_usd=...)` on an `Agent` whose model has no price (no `PriceTable` entry and a provider that does not report cost), at construction or at run start. See [Budget](/docs/architecture/budget#dollar-limits). | 500 |
| `TenantScopeRequiredError(operation)` | `ValueError` | The effective call has a state store under `Agent(strict_tenancy=True)` and omitted `tenant_id`, or a stored delegated child has no deliberately chosen outer scope, or any `reclaim` omitted it. An Agent without a store can run without a tenant id, silently. See [Multi-tenancy](/docs/architecture/multi-tenancy#strict-tenancy). | 500 |
| `GovernanceMismatchError(run_id, expected_digest=, actual_digest=, changed=)` | `RuntimeError` | A resume found different governance from the run's start and the Agent has `on_governance_change="raise"`. `changed` names the parts, never their contents. See [Governance](/docs/architecture/governance#detecting-changed-governance-on-resume). | 409 |
| `NoteLimitExceededError(run_id, limit)` | `ValueError` | `submit_note` on a run that already holds `max_notes_per_run` notes. | 409 |
| `ImageError(ValueError)` | `ValueError` | Base class of `InvalidImageError`, `ImageLimitError` and `ImageFetchError`; catch it for any bad image input. | 400 |
| `InvalidImageError(reason=, index=, media_type=, byte_length=)` | `ImageError` (`ValueError`) | An image failed validation at ingest: `reason` is `unsupported_type`, `type_mismatch`, `corrupt`, `animated`, `empty`, `purged`, `descriptor_version`, `descriptor_mismatch`, `bad_base64` or `path`. See [Images](/docs/recipes/images#errors). | 400 |
| `ImageLimitError(scope=, limit=, actual=, index=)` | `ImageError` | An image cap was exceeded (`image_bytes`, `source_bytes`, `image_side`, `image_pixels`, `message_count`, `request_count`, `request_bytes`, `estimated_tokens`, `many_image_dimension`, and `store_bytes` for a full in-memory store). | 413 |
| `ImageFetchError(reason=, host=, status_code=)` | `ImageError` | `Image.from_url` was refused or failed (`scheme`, `port`, `credentials`, `host_not_allowed`, `blocked_address`, `dns`, `redirect`, `timeout`, `too_large`, `http_status`, `content_encoding`, `disabled`, `connect`). Carries the host only, never the path or query. | 502 for `http_status` and `timeout`; otherwise 400 |
| `UnsupportedModalityError(provider=, model=, source=, ...)` | `RuntimeError` | The model cannot take images. `source` is `capability`, `catalog`, `adapter` or `provider_response`. | 400 |
| `ImageRejectedError(image_ids=, located=, retried=)` | `RuntimeError` | The provider refused a specific image. | 422 |
| `BlobNotFoundError(image_id)` | `LookupError` | The blob is missing, belongs to another tenant, or the run has no reference to it. The same error for all three. | 404 |
| `BlobIntegrityError(image_id, check=)` | `RuntimeError` | Stored bytes or a persisted descriptor do not match the catalog. | 500 |
| `ImagePersistenceUnsupportedError(reason=)` | `RuntimeError` | The state store has no blob catalog, an external blob row is read with no `blob_store`, or a tool returned images in a loop run without an image runtime. | 500 |
| `BlobContentionError(image_id)` | `RuntimeError` | Image storage lost a race with a concurrent purge or garbage collection. Transient; safe to retry. | 503 |
| `SkillValidationError(message, field=)` | `ValueError` | A [skill](/docs/architecture/skills) is built with an invalid name, description, file path, metadata, or frontmatter. `field` names the offender. | 400 |
| `SkillMissingError(run_id, missing=, mismatched=)` | `SkillContinuityError` | A paused run is continued on an agent that lacks a skill the run was created with. The run stays paused. | 409 |
| `SkillMismatchError(run_id, mismatched=)` | `SkillContinuityError` | Every skill is attached, but at least one has different content (digest) than the run was created with. The run stays paused. | 409 |

None of the image errors contain image bytes, base64 or a URL's query string, and they are raised without a chained exception. Each carries its arguments as attributes (`err.run_id`, `err.current_status`, etc.) for structured handling. `ContextLengthExceededError` carries `err.status_code`, `err.provider_code` and `err.model`. `SkillMissingError` and `SkillMismatchError` share the base class `SkillContinuityError` (a `RuntimeError`) and expose `err.missing` and `err.mismatched`; see the [resume contract](/docs/architecture/skills#resume-contract).

A few related exceptions live on the package root rather than `dendrux.errors`:

An `idempotency_key` collides with a different request fingerprint within the same tenant. The 0.3.0 methods reuse the hierarchy above. These are the cases worth knowing:

| Call | Raises |
| --- | --- |
| `submit_approval(decisions=...)` | `ValueError` for both or neither of `approved=` / `decisions=`, for `rejection_reason` with `decisions`, for a missing, unknown or duplicate call id, and for a non-`bool` `approved`. Raised before anything is claimed. |
| `submit_approval(approved=True, ...)` or `resume` approving a batch without `expected_pause_id=` | `InputValidationError` (field `expected_pause_id`, code `pause_id_required`) when the stored pause has an id. Under strict tenancy, denials and other continuations require the token too; legacy pauses without an id need no token. |
| `submit_resume(run_id)` | `PauseStatusMismatchError` when the run is paused for another reason (for example `waiting_approval`), plus the usual resume errors. |
| `request_pause(run_id)` | `RunNotFoundError`, `ValueError` for a bad `reason`. A `waiting_*`, `paused` or terminal run is a no-op, not an error. |
| `submit_note(run_id, text)` | `ValueError` for empty or oversized text or bad metadata, `NoteLimitExceededError` (a `ValueError`) when the run already holds `max_notes_per_run` notes, `RunNotFoundError`, `RunAlreadyTerminalError`. |
| `cancel_run(..., cascade=True)`, `request_pause`, `submit_note`, `RunStore.get_notes` or `RunStore.get_subtree` on a custom pre-0.3 `StateStore` | `NotImplementedError` naming the missing store method. Existing flows on such a store keep working. |
| `submit_tool_results`, `submit_input`, `submit_approval`, `submit_resume`, `resume` or `resume_stream` with `tenant_id=` | `RunNotFoundError` when the run is missing or belongs to another tenant, raised before anything is written. `resume_stream` raises it, and any store error from the tenant check, from the first iteration instead of yielding `RUN_ERROR`. |
| `RunStore.get_subtree`, `get_pending`, `follow`, `get_event_view` and a scoped `get_notes` for a missing or foreign run (the paged reads return empty results instead; see [RunStore](/docs/reference/run-store#tenant-scope)) | `RunNotFoundError`. | `retry(run_id, tenant_id=...)` | `RunNotFoundError` for a missing or foreign run (it was `ValueError` or `ReplayRunError` before 0.5.0). |
| `RunStore` reads, `get_pending` and `follow` with a bad id, tenant, cursor, limit, offset, filter or non-`bool` flag | `ValueError` with a fixed message that never echoes the rejected value (and a `read_argument_invalid` log line), before any query: ids and tenants are non-empty strings of at most 255 characters without NUL or lone surrogates; cursors fit 32 bits; at most 100 `event_types` or `status` entries; `metadata_filter` has at most 32 keys with scalar values; dates are timezone-aware. Map it to 400. `get_run(None)` raises too (it used to return `None`). |
| `Agent.get_result` with a malformed id or tenant | `ValueError` ("Invalid run_id." or "Invalid tenant_id."), before any query. |
| `MCPConnection.call_tool` | `MCPToolNotFoundError` for an unlisted tool name, `MCPToolCallError` for a server error result, `TimeoutError` when `timeout=` expires. See [MCP](/docs/architecture/mcp#calling-a-tool-directly). |
| `Agent(before_tool=...)` with `SingleCall` | `ValueError` at construction. |
| `run`, `stream` or any entry point with `tenant_id=""`, metadata keys starting with `dendrux.`, or input or metadata over the `Limits` caps | `ValueError` before anything is written. |
| A delegated run with a `tenant_id` different from its parent's | `ValueError` before the child run is created. |

## When a write fails inside a run

Dendrux writes a run's state as it goes: the run row, its events, traces, tool calls and usage. A failed write is retried where that is safe (see [Database retries](/docs/upgrading-to-0.6.0#database-retries)). What happens when it still fails after the retries depends on the write:

- **Four writes are best effort and never fail the run.** The record of a model call (`save_llm_interaction`), the usage row of a call (`save_usage`), the progress heartbeat of a legacy format-1 run (`touch_progress`) and the `guardrail.unmapped_placeholder` event, which notes a PII placeholder the run could not map back. If one cannot be written the run carries on and can finish `success`; the missing row is logged as a warning. The placeholder event is written just before the terminal write, and a failure to save it never discards a valid answer or leaves the run `running`. A write refused because the run lost its owner (fencing) is not best effort: it still stops the stale writer.
- **The other writes are fatal:** the run row, its events, traces and tool calls, and the final `finalize_with_event`. A fatal failure ends the call:
  - `agent.run` **raises `PersistenceError`**. It does not return a `RunResult`. Catch it in your route and answer 503; `retryable` says whether trying again may help.
  - `agent.stream` does not raise once the stream has started. It ends with a `run_error` event whose `error` is the fixed message `Database operation failed (persistence_error).` (A configuration, schema or startup failure before the first event can still raise.)

What the failed call leaves in the database depends on what the database can still do:

- If the run could not be created, no run exists.
- Dendrux then tries to record the failure. If the database answers again in time, the run is saved as `error` with the fixed message and a `run.error` event, even though the call raised: check the run's status before assuming it is still running.
- If the database still cannot be written, the run stays `running` at its last committed state: every event and row written before the failure is there, and nothing marks it `error`. Find it with `sweep` and move it on with `reclaim` (or finish it with `on_stale="error"`); see [Recovery](/docs/guides/recovery).

## When a commit acknowledgement is lost

`StoreOutcomeUnknown` means the connection broke during `COMMIT`, so the write may or may not have landed. Never assume you own a run after it. Treat it by operation:

| Call | What to do |
| --- | --- |
| `submit_tool_results`, `submit_input`, `submit_approval`, `resume` and other calls that claim a paused run | Do not run the claimed work and do not repeat the call straight away. The run is either still paused (the claim did not land) or claimed (by this attempt or by another caller). A repeat that gets `RunNotPausedError` tells you the run is no longer paused, but not who claimed it: it does not prove the first attempt won, so still do not assume ownership. Let the lease expire and let `sweep` and `reclaim` continue the run |
| `reclaim` | Do not retry the claim. The lease and the next `sweep` recover the run |
| `create_run` | The store proves the outcome from the run id you supplied plus the agent name, the tenant and the input (and the idempotency key and fingerprint, when you gave them). A matching run is reported as `created`; a proven absence is retried. If the identity conflicts but cannot be proven yours, you get `StoreOutcomeUnknown`: look the run up by id before creating another |
| Writes with a retry identity (traces, tool calls, events, usage, completions) | They read their rows back and normally report the real outcome. If that read-back also fails, they can end in `StoreOutcomeUnknown` too: repeat the write with the same identity once the database is reachable, which is safe, or check the run's state first |

On PostgreSQL the read-back waits for a concurrent writer for at most about five seconds (a transaction-local `lock_timeout`); if it times out the answer is `StoreOutcomeUnknown`, never a silent retry.

The message of `StoreOutcomeUnknown` is short and carries no database text. Use `err.code == "store_outcome_unknown"` in code and the `store_outcome_unknown` log line, which has the run id, for diagnosis.

## Provider errors

Every failed LLM request raises a `ProviderError` subclass (inside a run it ends the run `error` and is summarised as `RunResult.error_info`). Catch `ProviderError` and read `.category` and `.retryable`.

| Class | `category` | `retryable` default | Also a |
| --- | --- | --- | --- |
| `ProviderAuthError` | `auth` | no | |
| `ProviderRateLimitError` (`retry_after`) | `rate_limit` | yes | |
| `ProviderUnavailableError` | `unavailable` | yes | `ConnectionError` |
| `ProviderTimeoutError` | `timeout` | no | `TimeoutError` |
| `ProviderResponseError` | `rejected` | no | |
| `ProviderStreamIncompleteError` | `stream_incomplete` | no | |
| `ModelRefusalError` (`refusal_text`, in process only) | `refusal` | no | |
| `ContentFilteredError` | `content_filter` | no | |
| `ContextLengthExceededError` | `context_length` | no | |
| `ProviderError` itself | `credits`, `rejected`, `unknown` | by error | |

`safe_message` is a fixed template (`"{provider} {category} (HTTP {status}, code {provider_code})"`) that never contains vendor text, and is what `RunResult.error`, `agent_runs.error` and the `run.error` event carry. The vendor's own text lives only in debug traces and stored provider evidence, excluded from default contextual event views; raw store evidence remains operator-only. Image-path errors keep their sanitised `message`. The recipe is [Handling provider errors](/docs/recipes/handling-provider-errors).

Database failures use the same envelope: `ErrorInfo(category="persistence_error")` has no provider fields, and the run's `error` is a fixed message. A provider failure inside a custom provider, a grouped worker failure or a failed stream close is normalised to the `ProviderError` taxonomy at Dendrux's call sites; raise `ProviderError` subclasses from your own providers. Provider and model identifiers on these errors are bounded and control-free, and `provider_code` appears only when it looks like a code.

`ProviderResponseError` reports an empty normal completion (`empty_completion`) or a local stream bound (`stream_size_limit`, `stream_tool_call_limit`). It is not retryable. Tool-only output remains valid, and token-limit emptiness keeps its truncation flag.

A fenced stream observing a still-running owner ends its local feed with `RUN_ERROR` and `ErrorInfo(category="run_fenced", retryable=False)`. The result preserves the durable run status; this observation does not fail or mutate the winning run. Read its current state with `Agent.get_result` or `RunStore`. If the winner paused, the stale feed ends with `RUN_PAUSED` instead.

## MCP errors

MCP tool sources raise their own typed hierarchy under `MCPError`, importable from `dendrux.mcp`. The ones an application should be ready to handle — including `MCPCircuitOpenError` (fail-fast with `retry_after`), the capacity errors, and `MCPOutcomeUnknownError` (interrupted call the server may have applied; never retry automatically) — are tabulated with their semantics on the [MCP page](/docs/architecture/mcp#calls-errors-and-result-limits).

from fastapi import APIRouter, Depends, HTTPException
from dendrux.errors import (
    PauseStatusMismatchError, PersistenceNotConfiguredError,
    RunAlreadyClaimedError, RunAlreadyTerminalError,
    RunNotFoundError, RunNotPausedError,
)

@router.post("/runs/{run_id}/approval")
async def approval_route(run_id: str, body: dict, _=Depends(authorize)):
    try:
        result = await agent.submit_approval(
            run_id, approved=body["approved"], rejection_reason=body.get("rejection_reason"),
            expected_pause_id=body.get("pause_id"),    # required when approving a pause with an id
        )
    except RunNotFoundError:
        raise HTTPException(404, "run not found")
    except ValueError:    # includes InputValidationError (a missing pause_id, bad input)
        raise HTTPException(400, "invalid request")
    except (RunNotPausedError, PauseStatusMismatchError,
            RunAlreadyClaimedError, RunAlreadyTerminalError) as e:
        raise HTTPException(409, str(e))   # a stale pause_id lands here too
    except PersistenceNotConfiguredError:
        raise HTTPException(500, "persistence not configured")
    return {"status": result.status.value, "answer": result.answer}
