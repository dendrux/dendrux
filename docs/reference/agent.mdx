# Agent

`Agent` holds an agent's identity, capabilities, and limits, and exposes the runtime methods that execute it. Construct it once and reuse it across many runs.

```python
from dendrux import Agent
from dendrux.llm.anthropic import AnthropicProvider

agent = Agent(
    name="Support",
    provider=AnthropicProvider(model="claude-haiku-4-5"),
    prompt="You are a support agent.",
    tools=[...],
    database_url="sqlite+aiosqlite:///app.db",
)
```

`Agent` is an async context manager. Use `async with Agent(...) as agent:` so MCP sources, the provider, and any agent-owned engine close cleanly. All runtime methods are `async`.

## Constructor

```python
Agent(
    *,
    provider: LLMProvider,
    prompt: str,
    name: str = ...,                       # defaults to the class name
    tools: list[Callable] = [],
    tool_sources: list[MCPToolView | MCPSource | MCPServer | MCPHost] | None = None,
    max_iterations: int = 10,
    max_delegation_depth: int | None = None,
    loop: Loop | None = None,              # defaults to ReActLoop
    output_type: type[BaseModel] | None = None,
    database_url: str | None = None,
    database_options: dict[str, Any] | None = None,
    state_store: StateStore | None = None,
    deny: list[str] | None = None,
    require_approval: list[str] | None = None,
    budget: Budget | None = None,
    pricing: PriceTable | None = None,
    guardrails: list[Guardrail] | None = None,
    skills_dir: str | Path | None = None,
    skills: list[Skill] | None = None,
    deny_skills: list[str] | None = None,
    skill_executor: SkillExecutor | None = None,
    tool_result_transform: ToolResultTransform | None = None,
    before_tool: BeforeToolHook | None = None,
)
```

| Parameter | Purpose |
| --- | --- |
| `provider` | The LLM provider. Required. See [providers in the glossary](/docs/reference/api-glossary#providers). |
| `prompt` | The system prompt. Required (a subclass may set it as a class attribute instead). |
| `name` | Used for the run's owner and `cache_key_prefix`. Defaults to the class name. |
| `tools` | List of `@tool`-decorated functions. Empty for a pure chatbot. |
| `tool_sources` | MCP source declarations, compatibility servers, or shared hosts. See [MCP](/docs/architecture/mcp). |
| `max_iterations` | ReAct safety cap on LLM turns. Default 10. |
| `max_delegation_depth` | Max sub-agent nesting depth. |
| `loop` | `ReActLoop()` (default) or `SingleCall()`. See [Loops](/docs/architecture/loops). |
| `output_type` | A pydantic model for structured output. SingleCall only. |
| `database_url` | SQLAlchemy async URL. Enables persistence. Falls back to `DENDRUX_DATABASE_URL`. |
| `database_options` | Extra kwargs passed to `create_async_engine`. |
| `state_store` | An explicit `StateStore` instead of `database_url` (mutually exclusive). |
| `deny` | Tool names that can never execute. See [Access control](/docs/architecture/access-control). |
| `require_approval` | Server-tool names that pause for approval. See [Approval](/docs/architecture/approval). |
| `budget` | A `Budget(max_tokens=..., max_cost_usd=..., warn_at=..., on_exceed=..., include_children=...)`. Token and dollar limits with an optional pause or cancel. See [Budget](/docs/architecture/budget). |
| `pricing` | A `PriceTable` of USD-per-million-token rates used to fill `cost_usd` for providers that report tokens only. See [Cost and pricing](/docs/architecture/pricing). |
| `guardrails` | List of guardrails scanned each turn. See [Guardrails](/docs/architecture/guardrails). |
| `skills_dir` / `skills` / `deny_skills` | Skill loading and filtering. `skills_dir` is read lazily at the first run. See [Skills](/docs/architecture/skills). |
| `skill_executor` | A `SkillExecutor` subclass instance that runs skill scripts. Without it, `run_skill_script` is not offered to the model. See [Running scripts](/docs/architecture/skills#running-scripts). |
| `tool_result_transform` | Callable that rewrites a server tool's result before it is persisted or sent to the model. See [Transforming tool results](#transforming-tool-results). |
| `before_tool` | Sync or async policy hook, run once for each parsed tool call that passes static `deny=` and skill preflight, before approval; called with a `ToolCallContext`, returns a `ToolDecision` or `None`. Not supported with `SingleCall`. See [Tool policy hook](/docs/architecture/tool-policy). |

Construction validates its inputs: unknown names in `deny`/`require_approval`, `deny`/`require_approval` overlap, `output_type` without `SingleCall`, and tools with `SingleCall` all raise `ValueError`.

### Transforming tool results

`tool_result_transform` runs after every successful server-executed tool call — local `@tool` functions and MCP tools alike — and before the result is serialized. Whatever it returns becomes the result: the persisted `ToolInvocation.result`, the `TOOL` message the model sees, and the notifier/stream events all carry the transformed value.

```python
from dendrux import Agent, ToolResultContext

counter = 0

def tag_tables(ctx: ToolResultContext):
    global counter
    if not isinstance(ctx.result, list):
        return ctx.result            # always return something: ctx.result keeps it unchanged
    counter += 1
    return {"result_id": f"r{counter}", "rows": ctx.result}

agent = Agent(provider=provider, prompt="...", tools=[query_sales],
              tool_sources=[warehouse_view], tool_result_transform=tag_tables)
```

`ToolResultContext` is frozen and carries `tool_name`, `call_id`, `params`, `result` (the raw Python return value), `target`, and `meta` (the tool's `ToolDef.meta`; for MCP tools it includes `source_name`, `namespace`, and `mcp_tool_name`). Sync and async callables are both accepted.

- The return value always replaces the result. Return `ctx.result` to leave it unchanged — `None` is a real result, not "no change".
- If the transform raises, the tool call fails (`success=False`) with an error naming `tool_result_transform`; the model sees it as a tool error.
- It is not applied to failed tool calls, nor to results your client submits via `submit_tool_results`.
- It also runs for tools executed on resume after `submit_approval`.
- It runs on the raw result; guardrails scan the serialized tool message afterwards. MCP results arrive in their adapted form (e.g. `structuredContent` as `{"result": ...}`).
- Sync transforms run on the event loop, so keep them cheap.

## `run`

```python
async def run(
    user_input: str,
    *,
    history: list[ChatMessage] | None = None,
    activate_skills: Sequence[str] | None = None,
    tenant_id: str | None = None,
    metadata: dict[str, Any] | None = None,
    notifier: LoopNotifier | None = None,
    idempotency_key: str | None = None,
    output_type: type[BaseModel] | None = None,
) -> RunResult
```

Start a new run. Returns a [`RunResult`](/docs/reference/run-store#record-types) whose `status` is terminal (`success`, `error`, `cancelled`, `max_iterations`) or paused (`waiting_*`). `history` seeds prior conversation turns ([Chatbot threads](/docs/recipes/chatbot-threads)); `metadata` is opaque JSON stored on the run for your queries; `idempotency_key` requires persistence. `activate_skills` names skills to deliver in the run's first message instead of waiting for the model to call `use_skill`; unknown or denied names raise `ValueError` before any run is created ([Skills](/docs/architecture/skills#explicit-activate_skills)).

On success, `RunResult.answer` contains only the final answer turn after tool
use, not all assistant text produced during the run. `RunResult.commentary` is
the ordered list of non-empty assistant text from every step that ended in tool
calls (narration such as "Let me look that up"); it is `[]` for `SingleCall`,
for runs with no narration, and for idempotent cached results. Persisted traces
carry the same split as `TraceEntry.phase`. A paused run may instead carry a
clarification question.

Two ways to stop a `run()` in flight behave differently. Cancelling the task
awaiting it yourself (including via `asyncio.wait_for`) atomically finalizes a
still-running persisted run as `cancelled`, emits `run.cancelled` (reason
`task_cancelled`), and re-raises `CancelledError` (`wait_for` raises
`TimeoutError`); no `RunResult` is returned. Calling `agent.cancel_run(run_id)`
on the **same `Agent` instance in the same process** instead interrupts the
in-flight model call or tool and makes `run()` *return*
`RunResult(status=CANCELLED)` with `meta["interrupted"] = True` and
`meta["partial_output"] = False`. Existing paused or terminal outcomes are
preserved. Stream cancellation has the partial-answer semantics described below.
See [Cancellation](/docs/architecture/cancellation#interrupting-run).

A finished run's `RunResult.meta["undelivered_notes"]` lists inbox note ids it
never delivered (present only when there are any); see
[Inbox notes](/docs/architecture/inbox).

## `stream`

```python
def stream(
    user_input: str,
    *,
    history: list[ChatMessage] | None = None,
    activate_skills: Sequence[str] | None = None,
    tenant_id: str | None = None,
    metadata: dict[str, Any] | None = None,
    notifier: LoopNotifier | None = None,
    idempotency_key: str | None = None,
) -> RunStream
```

Same inputs as `run` (including `activate_skills`, validated before the stream is returned), but returns a `RunStream` immediately (no `await`). `stream.run_id` is available before iteration; with an idempotency key it is provisional until first iteration resolves the key. Iterate it for `RunEvent`s, or `.text()` for text deltas. Prefer `async with agent.stream(...) as s:` for deterministic cleanup. To interrupt from another coroutine, call `cancel_run(stream.run_id)`; the stream ends with `RUN_CANCELLED` carrying the partial answer. Closing the stream early also cancels the run and persists its current partial answer. Guardrails are not supported on the streaming path.

The final `RunResult.answer` contains the final answer turn only. On cancellation,
the partial answer contains only the current text buffer, which resets at every
`TOOL_RESULT`. It can be `None` even if earlier text was streamed. For example,
`"Checking…" → tool result → "The answer is 42"` yields an answer of
`"The answer is 42"`; cancellation immediately after the tool result can yield
`None`. `RunResult.commentary` holds the text of the tool steps that completed
before the cancellation. To retain the full transcript, accumulate `TEXT_DELTA`
events (or `.text()`) across all turns, or read persisted assistant messages with
`RunStore.get_traces()`. Traces contain recorded messages, not every delta from an
interrupted model call.

### Commentary vs final answer

Text a model writes before a tool call ("I'll start by exploring the
database…") streams as ordinary `TEXT_DELTA` events, so concatenating every
delta mixes narration into the answer. Each LLM-output and tool event carries
`iteration` (the loop step it belongs to; `None` on lifecycle events) and some
carry `phase`:

| Event | `iteration` | `phase` |
| --- | --- | --- |
| `TEXT_DELTA` | step number | Usually `None`. `"commentary"` when the text follows a tool block in the same step, or the provider's own label when it sends one (OpenAI Responses `phase`). Always `"final_answer"` for `SingleCall`. |
| `REASONING_DELTA` | step number | `None` |
| `TOOL_USE_START`, `TOOL_USE_END`, `TOOL_RESULT` | step number | `"commentary"`: the text of this step was narration. |
| `RUN_COMPLETED` | `None` | `"final_answer"` on success; `None` for `max_iterations`. |

A text block streams before the tool call that makes it commentary, so the
phase of a delta is usually unknown when it arrives. Clients buffer instead:

```python
buckets: dict[int, list[str]] = {}
commentary: set[int] = set()
async with agent.stream("...") as stream:
    async for event in stream:
        if event.type == RunEventType.TEXT_DELTA:
            buckets.setdefault(event.iteration, []).append(event.text)
        elif event.phase == "commentary":
            commentary.add(event.iteration)       # that step's text was narration
        elif event.type == RunEventType.RUN_COMPLETED:
            answer = event.run_result.answer       # authoritative final answer
            narration = event.run_result.commentary
```

Render a bucket provisionally as it streams, restyle it as progress when a
commentary event arrives for its step, and treat the remaining bucket as the
answer when `RUN_COMPLETED` carries `phase="final_answer"`. Persist
`run_result.answer`, not the concatenated deltas. After the fact the same
split is on `TraceEntry.phase` (`RunStore.get_traces()`) and on the
`phase` field of each `llm.completed` event in the durable event log.

`idempotency_key` uses the same persistence requirement and request fingerprint
as `run()` (agent name, input, history, context, and output type). A matching
terminal run yields **one terminal event** with its original ID and cached summary
result, without calling the provider or replaying text/tool events. Read
`stream.result.answer` after iteration; `.text()` yields nothing on a cache hit.
Cached `error` and `cancelled` outcomes use `RUN_ERROR` and `RUN_CANCELLED`;
`success` and `max_iterations` use `RUN_COMPLETED` with their original status.

Active-run matches and fingerprint conflicts yield `RUN_ERROR`, with
`stream.result.meta["error_type"]` equal to `RunAlreadyActiveError` or
`IdempotencyConflictError`. Missing persistence yields `RUN_ERROR` during setup.
These errors do not change the original run or its event log. Before using the
ID for cancellation or correlation, consume the first event so the key has been
resolved. The cached result is a summary, like `run()`'s cached result; it does
not reconstruct the original steps.

[`examples/33_cost_cancel_idempotency.py`](https://github.com/dendrux/dendrux/blob/main/packages/python/examples/33_cost_cancel_idempotency.py) exercises the cache hit and the conflict path against a persisted store.

## `resume`, `submit_tool_results`, `submit_input`, `submit_approval`, `submit_resume`

The submit family resumes a paused run. Each one matches a pause status (see [Pause and resume](/docs/architecture/pause-resume)). All require persistence and the run to exist.

```python
async def submit_tool_results(run_id: str, results: list[ToolResult], *, notifier=None) -> RunResult
async def submit_input(run_id: str, text: str, *, notifier=None) -> RunResult
async def submit_approval(
    run_id: str,
    *,
    approved: bool | None = None,
    decisions: Mapping[str, ApprovalDecision] | None = None,
    rejection_reason: str | None = None,
    notifier=None,
) -> RunResult
async def submit_resume(run_id: str, *, notifier=None) -> RunResult
async def resume(run_id: str, *, tool_results=None, user_input=None, notifier=None) -> RunResult
```

| Method | Resumes | Raises |
| --- | --- | --- |
| `submit_tool_results` | `waiting_client_tool` | `InvalidToolResultError` on id mismatch; the shared resume errors below. |
| `submit_input` | `waiting_human_input` | the shared resume errors below. |
| `submit_approval` | `waiting_approval` | `ValueError` for an invalid argument combination or decision ids (before anything is claimed); the shared resume errors below. |
| `submit_resume` | `paused` (requested or budget pause) | the shared resume errors below. |
| `resume` | generic resume entry point; with no payload it continues a `paused` run or approves a `waiting_approval` batch | same. |

`submit_approval` takes exactly one of `approved=` (whole batch) or `decisions=` (per call, `ApprovalDecision.approve()` / `ApprovalDecision.deny(reason)` keyed by call id). Client-target calls in the batch are never executed on the server; the run pauses again as `waiting_client_tool` for them. See [Approval](/docs/architecture/approval).

If the run was created with skills, these methods first compare them with the skills on this agent and raise `SkillMissingError` or `SkillMismatchError` (leaving the run paused) when they differ; `resume_stream` ends with a `RUN_ERROR` instead. See [Resume contract](/docs/architecture/skills#resume-contract).

Shared resume errors: `RunNotFoundError`, `RunNotPausedError`, `PauseStatusMismatchError`, `RunAlreadyClaimedError`, `RunAlreadyTerminalError`, `PersistenceNotConfiguredError`. See [Errors](/docs/reference/errors).

## `cancel_run`

```python
async def cancel_run(
    run_id: str,
    *,
    cascade: bool = False,
    tenant_id: str | None = ...,    # omitted = unscoped
) -> RunResult
```

Request cancellation. Works for paused runs (atomic CAS to `cancelled`, including `paused`), running runs (cooperative flag), batch `run()` calls and streamed runs this instance owns (in-process interrupt: the in-flight model call or tool is abandoned; `run()` returns `CANCELLED` with `meta["interrupted"]`, a stream ends with `RUN_CANCELLED` carrying the partial `answer`), and terminal runs (no-op, never raises). Returns the persisted state at the time of the request; a non-terminal `status` with `meta["cancel_requested"] == True` means "requested, not yet stopped".

`cascade=True` also cancels every non-terminal descendant, deepest first and `run_id` last, over a point-in-time snapshot; per-run outcomes are in `meta["cascade"]`. `tenant_id=` requires the run to belong to exactly that tenant (`None` = untenanted) or `RunNotFoundError` is raised, and limits the cascade to the same tenant. A cancel that arrives after the run's last checkpoint does not stop a run that then completes successfully. Raises `RunNotFoundError` and `PersistenceNotConfiguredError`. See [Cancellation](/docs/architecture/cancellation).

## `request_pause`

```python
async def request_pause(
    run_id: str,
    *,
    cascade: bool = True,
    tenant_id: str | None = ...,    # omitted = unscoped
    reason: str | None = None,       # at most 1000 characters
) -> PauseOutcome
```

Ask a running run to pause durably at its next checkpoint (the top of its next iteration, or between the approved calls of a resumed batch). It never preempts a model call or tool. The run becomes `paused`, `run.paused` is written with `reason="requested"`, and the waiting `run()` or stream returns a paused result. Resume with `submit_resume`. A `waiting_*`, `paused` or terminal run is a no-op; cancellation wins over a pause. `cascade=True` (the default) flags every non-terminal descendant too, which is **flag propagation only, not a resumable call stack**: a paused child returns its paused result to the delegating tool, and resuming the child never rewrites what the parent recorded.

`PauseOutcome` has `run_id`, `status_before`, `status_after` and `affected`, a list of `(run_id, outcome)` with outcome `requested`, `already_waiting`, `already_paused` or `terminal`, deepest descendants first and `run_id` last. Raises `RunNotFoundError`, `PersistenceNotConfiguredError` and `ValueError` (bad `reason`). See [Pause and resume](/docs/architecture/pause-resume#requesting-a-pause).

## `submit_note`

```python
async def submit_note(
    run_id: str,
    text: str,
    *,
    metadata: Any = None,
    tenant_id: str | None = ...,    # omitted = unscoped
) -> str
```

Leave a note for a non-terminal run; returns the note id. The runner delivers pending notes at the top of its next iteration as a user message `NOTE FROM USER:\n{text}` and writes an `inbox.delivered` event. Delivery is at-least-once; notes still pending when the run ends are listed in `RunResult.meta["undelivered_notes"]` and readable with `RunStore.get_notes`. `text` is non-empty and at most 32 KiB as UTF-8; `metadata` must be JSON and at most 8 KiB encoded, and is never shown to the model. Raises `ValueError`, `PersistenceNotConfiguredError`, `RunNotFoundError` and `RunAlreadyTerminalError`. See [Inbox notes](/docs/architecture/inbox).

## Heartbeat

```python
from dendrux import heartbeat, aheartbeat

def heartbeat() -> None            # sync, fire-and-forget, thread-safe
async def aheartbeat() -> None     # awaits the write
```

Call it from inside a tool that waits a long time (a human, a slow job) to refresh persisted progress and reduce the risk of a [stale-run sweep](/docs/architecture/state-persistence#long-running-tools-and-the-stale-sweep) reaping the run. Writes are best-effort and failures are logged; both helpers are no-ops outside a persisted run. `heartbeat()` works from async tools and from sync tools (which run in a worker thread) and coalesces calls less than a second apart; `aheartbeat()` must be awaited on the run's event loop and logs, never raises, on failure.

## `retry`

```python
async def retry(run_id: str, *, tenant_id=None, metadata=None, notifier=None, **kwargs) -> RunResult
```

Start a fresh run that reuses an existing terminal run's input and approximate prior context. Requires persistence. The source run must belong to `tenant_id`, otherwise `ReplayRunError` is raised. Skills the source run activated explicitly stay activated; if one is no longer attached, `retry` raises `ValueError` before creating a run.

## `close`

```python
async def close() -> None
```

Close directly owned MCP sources, the provider, and any agent-owned engine. Called for you by `async with Agent(...)`. Leases on shared MCP connections (`MCPRuntime` views, `MCPHost`) are released, never closed; the application closes its runtime or host at worker shutdown. The shared global engine from `DENDRUX_DATABASE_URL` is not disposed because it is not agent-owned.
