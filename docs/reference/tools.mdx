# Tools

A tool is a plain Python function decorated with `@tool()`. Dendrux reads the signature, type hints, and docstring once, at decoration time, and stores the result on a `ToolDef`. The function stays callable as normal.

```python
from typing import Literal

from dendrux import tool


@tool()
async def show(kind: Literal["chart", "table"], title: str | None = None) -> str:
    """Render a chart or table in the UI.

    Args:
        kind: Which widget to render.
        title: Optional heading shown above the widget.
    """
    return f"rendered {kind}"
```

The tool's `description` is the full docstring. The arguments schema is generated from the type hints.

## Decorator options

| Option | Default | Meaning |
| --- | --- | --- |
| `target` | `"server"` | `"server"` runs the function in your process; `"client"` pauses the run and hands the call to your client. |
| `parallel` | `True` | Whether calls to this tool may run concurrently with others. |
| `max_calls_per_run` | `None` | Limit on calls per run. `None` = unlimited. |
| `timeout_seconds` | `120.0` | Execution timeout for server tools. |
| `parameters` | `None` | Explicit JSON Schema for the arguments. Skips generation from type hints. |
| `strict` | `False` | Opt into strict tool calling on OpenAI and Anthropic. See [Strict mode](#strict-mode). |
| `receives_pii` | `False` | With `PII(restore="allowlisted")`, `True` (or a set of entity names such as `{"EMAIL_ADDRESS"}`) lets this tool receive real values in place of placeholders. See [PII restore](/docs/architecture/pii-restore). |

## Supported parameter types

| Python type | JSON Schema |
| --- | --- |
| `str`, `int`, `float`, `bool` | `string`, `integer`, `number`, `boolean` |
| `list[T]` | `{"type": "array", "items": <T>}` |
| `dict`, `dict[str, Any]` | `{"type": "object"}` |
| `dict[str, T]` | `{"type": "object", "additionalProperties": <T>}` |
| `Literal["a", "b"]` | `{"type": "string", "enum": ["a", "b"]}`. The type is taken from the values, and all values must share one JSON type. |
| `enum.Enum` subclass | An enum of the member **values**, typed like `Literal`. |
| pydantic `BaseModel` | The model's `model_json_schema()`, with `$defs` / `$ref` inlined so the schema is self-contained. |
| `@dataclass` | A nested object. Fields without defaults are required. |
| `TypedDict` | A nested object. Keys in `__required_keys__` are required, so `NotRequired[...]` is honored. |
| `T \| None` / `Optional[T]` | A nullable `T`, for example `{"type": ["string", "null"]}`. For an `enum`, `null` is added to the values. |
| `Annotated[T, ...]` | The schema for `T`, plus a description (see below). |

Nested types compose. For example, `list[Node]` where `Node` is a `BaseModel` becomes an array of typed objects.

A parameter is **required** when it has no default and is not `Optional`. Defaults must be JSON-serializable and are emitted as `"default"`.

Some types are rejected at decoration time with a `TypeError` that names the parameter:

- Unions other than `T | None`, for example `str | int`
- `Literal` or `Enum` values of mixed types, for example `Literal["a", 1]`
- `dict` with non-`str` keys
- Recursive models, dataclasses, or TypedDicts, because they cannot be inlined
- Any other custom class

For any of these, pass the schema yourself with `parameters=`.

> **Arguments are validated and coerced (0.5.0).** A `BaseModel` parameter receives the model instance, an `Enum` parameter receives the member, and values are converted to the annotated types. See [How arguments are checked](#how-arguments-are-checked). Before 0.5.0 these arrived as plain JSON values (`dict`, raw value) and you had to validate them yourself.

> **Malformed arguments never reach your tool.** If the model's arguments are not valid JSON, the call is rejected before parameter validation with `code: "invalid_json"`. The model sees the parse error and retries; the run does not fail, and the raw arguments are never persisted. See [Tool argument validation](/docs/architecture/loops#tool-argument-validation).

## Parameter descriptions

There are two ways to describe a parameter. If both are present for the same parameter, `Annotated` wins.

**`Annotated` metadata**: use either a pydantic `Field(description=...)` or a plain string.

```python
from typing import Annotated
from pydantic import Field


@tool()
async def search(
    query: Annotated[str, Field(description="Full-text search query")],
    limit: Annotated[int, "Maximum number of results"] = 10,
) -> list[str]:
    """Search the catalog."""
    ...
```

**Google-style docstring `Args:` section**: Dendrux reads lines of the form `name: text` and `name (type): text`. Indented continuation lines are joined to the line above. Entries for names that are not parameters are ignored. The docstring itself stays unchanged as the tool's `description`.

## How arguments are checked

For a local `@tool`, each call goes through these steps in order, and a failure at any step returns an error to the model instead of running your function:

1. The arguments string is parsed as JSON (`code: "invalid_json"` on failure).
2. `deny=` is applied.
3. PII placeholders are restored, if your PII guardrail and `restore=` mode allow it for this tool.
4. The arguments are validated against the tool's JSON Schema. Integral floats such as `3.0` are accepted for `integer`.
5. They are coerced to the annotated types: `3.0` becomes `3`, a dict becomes the `BaseModel`, dataclass or `TypedDict`, a string becomes the `Enum` member, an ISO 8601 string becomes a `datetime`, and `Field(...)` constraints (`ge`, `le`, `min_length`, `max_length`, `pattern` and so on) are enforced. The constraints also appear as keywords in the generated schema.
6. `max_calls_per_run` is checked.
7. `before_tool` runs.
8. If approval is needed, the run pauses.
9. Your function runs.

Validation happens before the approval pause, so a person is never asked to approve a call that could not have run.

**What a reviewer sees, and what runs.** Your function is called with objects built from the coerced arguments, and `before_tool` receives real values in process. The approval view (`approval.requested` and any stored or displayed approval) carries the arguments exactly as the model sent them: after JSON parsing, in placeholder form when PII redaction is on, before coercion, and without injected defaults. Coercion is deterministic, so the approved arguments decide what runs.

```python
from pydantic import BaseModel, Field

class Address(BaseModel):
    city: str
    zip: str = Field(pattern=r"^\d{5}$")

@tool()
async def ship(order_id: int, to: Address) -> str:
    """Ship an order."""
    return f"{order_id} -> {to.city}"     # `to` is an Address, not a dict
```

Details:

- Error messages name the field and the constraint that failed, never the value, so personal data cannot flow back to the model provider through an error.
- `*args` and `**kwargs` are left out of the generated schema.
- A tool with an explicit `parameters=` schema keeps JSON Schema validation only. There is no coercion, and your function receives the plain JSON values.
- MCP tools and client tools are not coerced: their arguments and results are unchanged from 0.4.
- Tool schemas are part of the prompt, so adding constraint keywords can change a prompt-cache key once, on the first request after you upgrade.

## Timeouts and the thread pool

`timeout_seconds` bounds each server tool call. How a timeout behaves depends on whether the call had started:

| Situation | The model sees | Safe to retry? |
| --- | --- | --- |
| The call was still queued when the timeout hit | `code: "timeout_not_started"` | Yes, it never ran |
| The call had started | `code: "timeout_outcome_unknown"`, with text warning not to blindly retry tools with side effects | No, it may have completed |

Sync tools (plain `def` functions) run on one process-wide, bounded thread pool, created on first use. Size it with `DENDRUX_TOOL_THREADS` (default 32). Limit what one `Agent` can occupy with `Agent(tool_threads=8)` (default 8), so one agent or tenant cannot starve the others. Pool threads are daemon threads: a hung sync tool never blocks interpreter exit, but its side effect may be cut off at exit.

A sync tool that has timed out cannot be killed; it keeps its thread until it returns. Dendrux counts these and reports them in a log line and on the `tool.completed` event, and a public helper returns the current number so you can export it as a gauge. Async tools are cancelled at the timeout.

If a parallel batch ends the run (a failure that stops the run), the async siblings are cancelled and recorded as `cancelled`; sibling sync tools that had already started are recorded with an unknown outcome.

## Result size limits

A tool result larger than `Limits.max_tool_result_bytes` (1 MiB by default) is replaced before it is stored or sent to the model. A JSON result becomes `{"error": "result too large", "code": "size_limit", "bytes": N}`; a plain string result is truncated with a marker. The same cap applies to local, MCP and client-submitted results.

```python
from dendrux import Agent, Limits

Agent(provider=provider, prompt="...", tools=[export_csv],
      limits=Limits(max_tool_result_bytes=8 * 1024 * 1024))
```

Return a summary, a count, or a file reference from the tool and let the model ask for more, rather than raising the cap. The other limits (`max_input_bytes`, `max_metadata_bytes`, `max_notes_per_run`) are on the [Agent](/docs/reference/agent#limits) page.

## Explicit schema: `parameters=`

When the generated schema does not fit, pass your own JSON Schema. Generation is skipped entirely and the schema is stored as given. The root must be a dict with `"type": "object"`.

```python
@tool(parameters={
    "type": "object",
    "properties": {"value": {"anyOf": [{"type": "string"}, {"type": "number"}]}},
    "required": ["value"],
})
async def record(value) -> str:
    """Record a value."""
    ...
```

## Strict mode

`@tool(strict=True)` opts the tool into strict tool calling: [OpenAI strict function calling](https://platform.openai.com/docs/guides/function-calling#strict-mode) and [Anthropic strict tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use). With strict mode on, the provider constrains the model's arguments to the schema.

The schema is normalized once, at decoration time, and stored on `ToolDef.parameters`, so every provider sees the same schema:

- Every object gets `additionalProperties: false`.
- Every property becomes required. `Optional` parameters are already nullable, so the model can still pass `null`.
- A parameter that has a non-`None` default, such as `limit: int = 10`, also becomes required. The model must then supply a value, and the default appears only as a `"default"` hint in the schema.

On the wire:

| Provider | Behavior |
| --- | --- |
| `OpenAIProvider`, `OpenRouterProvider` (Chat Completions) | Sends `"strict": true` on the function. |
| `OpenAIResponsesProvider` | Sends `"strict": true` on the function tool. |
| `AnthropicProvider` | Sends `"strict": true` with a copy of the schema adapted to Anthropic's strict subset (see [Strict mode on Anthropic](#strict-mode-on-anthropic)). |

OpenAI strict mode requires every object to declare its properties. If a strict tool has a free-form `dict` or `dict[str, T]` parameter, the decorator raises `TypeError`. Use a `BaseModel`, dataclass, or `TypedDict` instead.

`strict=True` combines with `parameters=`: your explicit schema is normalized the same way. The decorator also rejects a free-form object under draft-7 `definitions`, the same as under `$defs`.

### Strict mode on Anthropic

On Anthropic, Dendrux sends `"strict": true` and a per-request copy of the schema adapted to Anthropic's strict subset. `ToolDef.parameters` is not changed. Non-strict tools are sent exactly as before, byte for byte, so prompt caching is not affected.

The adapted copy:

- Gets `additionalProperties: false` on every object.
- Keeps what the grammar can enforce: `enum`, `const`, `$ref`, optional fields, `minLength`, `maxLength`, simple `pattern`s, `minItems` of 0 or 1, and the standard `format`s (`date-time`, `date`, `time`, `duration`, `email`, `hostname`, `uri`, `ipv4`, `ipv6`, `uuid`).
- Moves what Anthropic rejects into the field's `description`, so the model still sees it: numeric bounds (`minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`), `multipleOf`, `maxItems`, `minItems` above 1, `uniqueItems`, uncommon `format`s, and advanced regex features such as lookaround. A bound like `Field(ge=1)` becomes the text "Must be >= 1." in the description.

A constraint that was moved into the description is a hint to the model, not a grammar rule. If it matters, check it in your function.

Anthropic limits one request to 20 strict tools, 24 optional parameters and 16 union-typed parameters (`X | None`, `anyOf`) across all strict tools. Dendrux counts these in tool order. A tool is sent non-strict, with the reason logged on `dendrux.llm.anthropic`, when it:

- would go over a limit;
- has a free-form `dict`, a tuple, an `Any` field or a recursive model.

A strict tool that is sent non-strict logs a WARNING once per tool name, then DEBUG.

If Anthropic still rejects a strict schema (its grammar compiler has size and regex limits that cannot be checked in advance), Dendrux retries that request once with every strict tool sent as before. It logs a WARNING and keeps sending that tool non-strict for the rest of the process. The retry applies to any HTTP 400 on a request that carried a strict tool; other errors are raised unchanged.

To turn strict mode off for a provider, pass `strict=False`:

[//]: # "docs-test: skip - fragment: relies on `AnthropicProvider`, defined by setup shown elsewhere"

```python
provider = AnthropicProvider(model="claude-sonnet-4-6", strict=False)
```

Then tools and structured output are sent exactly as in 0.4.0. Use it when you point `ANTHROPIC_BASE_URL` at a gateway that rejects the `strict` field.

**Data retention.** Strict mode sends your tool schemas to Anthropic's grammar compiler, which caches them for up to 24 hours since last use. That cache is separate from prompts and responses, which keep their usual zero-data-retention and HIPAA handling. Do not put sensitive data such as PHI in property names, `enum` or `const` values, or `pattern`s. If your schemas may contain it, use `AnthropicProvider(..., strict=False)`. See Anthropic's [strict tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use) and [structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs) pages, under "Data retention".

Apps that already used `@tool(strict=True)` with Anthropic see one prompt-cache miss after upgrading to 0.4.1, because the tool payload now carries `strict` and the adapted schema.

## When the model calls a tool that does not exist

The call does not run. The model gets a failed tool result that lists what it can call:

```text
Unknown tool: bash. Available tools: read_file, write_file
```

Names are sorted and capped at 50, then `, … and N more`. If no tools were offered, the text is `Unknown tool: bash. No tools are available.` The `Unknown tool: <name>` prefix is stable.

## MCP tools

Tools discovered from MCP servers do not go through `@tool`. Their server-provided `inputSchema` is passed to the model unchanged, and strict mode does not apply to them.
