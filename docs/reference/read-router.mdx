# make_read_router

`make_read_router` builds a read-only FastAPI `APIRouter` over a [`RunStore`](/docs/reference/run-store). Mount it into your app and you get the full read surface (list, detail, events, SSE, drill-downs) with one auth dependency and one tenant resolver.

> **Frozen in 0.5.** The router stays and works, but it gets no new features, and it is not deprecated. Whether to deprecate it is decided in 0.6, from how it is used. For anything beyond a quick dashboard, build your own read routes on `RunStore.get_pending` and `RunStore.follow`; the router is a thin wrapper over the same calls. See [Build your own read routes](/docs/recipes/build-your-own-read-routes).

```python
from dendrux.http import make_read_router
```

## Signature

```python
def make_read_router(
    *,
    store: RunStore,
    authorize: Callable[..., Any],
    tenant_resolver: Callable[..., Any] | UNSCOPED,
    include_payloads: bool = False,
    sse_max_connections: int = 500,
    sse_max_duration_s: float = 900,
) -> APIRouter
```

| Parameter | Meaning |
| --- | --- |
| `store` | The `RunStore` the router reads from. |
| `authorize` | A FastAPI dependency. Raise `HTTPException` to deny; return anything (ignored) to allow. Runs on every route except `/health`. |
| `tenant_resolver` | **Required.** A FastAPI dependency that returns the caller's scope: a non-empty `str` (that tenant), `None` (untenanted runs only) or `UNSCOPED` (every tenant). Pass the `UNSCOPED` sentinel itself, instead of a function, for a single-tenant app. See [Tenant resolver](#tenant-resolver). |
| `include_payloads` | `False` by default. When `True`, responses include raw payloads. See [Payloads](#payloads). |
| `sse_max_connections` | Most concurrent SSE connections this router serves, per process. The next connection gets 503. Default 500. |
| `sse_max_duration_s` | Longest one SSE connection stays open, in seconds. It then closes with a cursor so the client reconnects. Default 900. |

Returns a plain `APIRouter`. You own the prefix, CORS, TLS, rate limiting, and middleware. Write routes (submit / cancel) are yours to build on `Agent` methods.

A bad value for any of these raises `TypeError` or `ValueError` when the router is built, not on a request.

## Mount

```python
from fastapi import Depends, FastAPI, HTTPException, Request
from dendrux.http import make_read_router
from dendrux.store import RunStore

app = FastAPI()
store = RunStore.from_database_url("sqlite+aiosqlite:///app.db")

async def authorize(request: Request) -> None:
    if request.headers.get("authorization") != f"Bearer {TOKEN}":
        raise HTTPException(401, "unauthorized")

async def tenant_resolver(request: Request) -> str:
    return request.state.org_id          # set by your auth layer

app.include_router(
    make_read_router(store=store, authorize=authorize, tenant_resolver=tenant_resolver),
    prefix="/api",
)
```

Single-tenant app:

```python
from dendrux import UNSCOPED

app.include_router(
    make_read_router(store=store, authorize=authorize, tenant_resolver=UNSCOPED),
    prefix="/api",
)
```

## Tenant resolver

The resolver is a normal FastAPI dependency, so it can read headers, the session or the token claims that `authorize` verified. Its return value scopes every read on every route:

| Returns | The caller can read |
| --- | --- |
| `"acme"` | only runs with `tenant_id == "acme"` |
| `None` | only untenanted runs |
| `UNSCOPED` | all runs (an operator view). `?tenant_id=` on `GET /runs` then narrows the list |

- Any other return value (an empty string, an int, a dict) is a 500. The router fails closed.
- The scope is applied inside the same SQL query as the read. A run outside the scope returns exactly the same 404 body as a run that does not exist.
- For a scoped caller `?tenant_id=` is ignored. It cannot widen the view.
- A resolver that returns `UNSCOPED` makes that caller an all-tenant reader. Give it only to your own operators.
- The resolver must return a plain value; a dependency written with `yield` is not supported.

See [Multi-tenancy](/docs/architecture/multi-tenancy).

## Payloads

By default the router does not return raw payloads. With `include_payloads=False`:

| Hidden | Where it would have appeared |
| --- | --- |
| Provider request and response | `/llm-calls` |
| Raw traces | `/traces` |
| Tool results and server-tool parameters | `/tool-calls` and other events |
| The system prompt | `run.started` event data |
| Arguments of **past** pauses | `run.paused` events and `/pauses` |
| The PII mapping | run detail and `/pauses` |

**Not hidden: the active pause.** While a run is paused, the pending arguments stay visible by default: the parameters of a pending client-tool call, and the arguments of an approval or input request. They are what the client must act on. This covers `run.paused` on `/events`, SSE and follow, the last unresumed pair on `/pauses`, and `RunStore.get_pending`. Approval and input requests show the arguments as the model sent them (placeholder form when PII redaction is on).

This applies to `/runs/*`, `/events`, SSE and `/pauses`. Statuses, counts, timings, token usage, costs and event types are always returned. Set `include_payloads=True` for a trusted internal viewer, behind the strongest `authorize` you have.

## Endpoints added

| Method + path | Returns |
| --- | --- |
| `GET /health` | `{"status": "ok"}` (unauthenticated, for probes) |
| `GET /runs` | Filtered, paginated run list (`offset` at most 10,000; larger is a 422) |
| `GET /runs/{run_id}` | One run's detail (404 if unknown or out of scope) |
| `GET /runs/{run_id}/events` | Paginated event log (`?after=N` cursor) |
| `GET /runs/{run_id}/events/stream` | Server-Sent Events stream |
| `GET /runs/{run_id}/llm-calls` | Per-LLM-call records (default 50, at most 200) |
| `GET /runs/{run_id}/tool-calls` | Per-tool-execution records |
| `GET /runs/{run_id}/traces` | Conversation messages in order |
| `GET /runs/{run_id}/pauses` | Pause/resume pairs |

Run summaries and details include `tenant_id`; details include `error_info` when a provider failure ended the run. Date filters (`started_after`, `started_before`) must carry a timezone; a naive datetime is a 422.

## SSE behaviour

- The stream closes after an `event: end` frame once the run is terminal and every event has been sent. Reconnecting to a finished, drained run returns HTTP 204. Add `?follow=true` to keep the stream open as in 0.4.
- Connections to the same run share one polling query inside your process, so database load follows the number of watched runs, not the number of open connections.
- A connection closes after `sse_max_duration_s` with a cursor; authorisation and the tenant resolver run again when the client reconnects.
- Idle polling backs off from 0.5 to 2 seconds.
- The limit is per process. With several workers, the total is the sum.

Size your pool for it. As a rule of thumb budget about one query per second per watched run, and give the router its own small engine (`RunStore.from_database_url(...)`) when you serve many viewers, so event reads never compete with the agents for connections. Postgres `LISTEN/NOTIFY` push is planned for 0.6.
