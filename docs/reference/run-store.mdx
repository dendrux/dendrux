# RunStore

`RunStore` is the public, read-only way to query everything Dendrux persisted about a run. It is a plain Python object you can call from any code (routes, admin scripts, background jobs) it supports routes and inspection tools owned by your app.

[//]: # "docs-test: skip - fragment: needs an existing database and a real run id"

```python
import asyncio

from dendrux.store import RunStore


async def main(run_id: str) -> None:
    async with RunStore.from_database_url("sqlite+aiosqlite:///app.db") as store:
        run = await store.get_run(run_id)
        events = await store.get_events(run_id, limit=100)   # one page; see Bounded list reads
        print(run, len(events))


asyncio.run(main("01J..."))   # the id of a run in app.db
```

## Constructors and lifecycle

[//]: # "docs-test: skip - API signature listing, not runnable code"

```python
RunStore(state_store: StateStore, *, blob_store: BlobStore | None = None)   # listens when the store has live updates
@classmethod
def from_database_url(database_url: str, *, blob_store: BlobStore | None = None,
                      database_options: dict[str, Any] | None = None) -> RunStore   # RunStore owns the engine; never listens
@classmethod
def from_engine(engine: AsyncEngine, *, blob_store: BlobStore | None = None) -> RunStore   # caller owns the engine; never listens
async def close() -> None
```

`RunStore(store)` wraps a store you built, such as `RunStore(PostgresStateStore(engine, live_updates=True))`. It takes any `StateStore`, including your own. The two class methods build a store for you and never enable live updates, so a follower made by `RunStore.from_engine(engine)` polls even when your writers announce on a bus. If you meant to listen, replace it with `RunStore(store_for_engine(engine, live_updates=...))` or, better, the same store object your `Agent` uses.

Every form takes `blob_store=` (a `BlobStore`) when the deployment keeps image bytes outside the database; use the same store as the `Agent`. `from_database_url` also takes `database_options=` (extra `create_async_engine` options; non-SQLite engines default to `pool_pre_ping=True` and `pool_recycle=1800`). It refuses a `live_updates` key in them with a `ValueError`, even with the value `None` or `False`: build the store yourself and pass it to `RunStore(store)`. Two members relate to images:

[//]: # "docs-test: skip - API signature listing, not runnable code"

```python
store.blobs                                                       # BlobAccessor: read, info, references, purge, collect_garbage
async def read_image(run_id: str, sha256: str, *, tenant_id=...) -> bytes
```

`read_image` returns verified image bytes only if the run exists (and matches `tenant_id` when given) and references that blob; otherwise `BlobNotFoundError`, the same error for a missing blob, another tenant's blob and an unreferenced one. It is the call to put behind your own authorization when you serve images from a route. `store.blobs.purge(...)` and `store.blobs.collect_garbage(...)` are the only writes `RunStore` has. See [Images](/docs/recipes/images#storage).

`from_database_url` creates and owns an engine; `close()` (or exiting the `async with`) disposes it. `from_engine` and `RunStore(store)` leave engine ownership with you. Closing any of them also stops its live feed. `RunStore` is an async context manager.

**Live updates.** Only `RunStore(store)` listens, and only when `store.live_updates` is set (see [Scaling](/docs/guides/scaling#live-updates)). It takes a listener lease the first time you call `follow()` or `stream_events()`; `close()` releases that lease and never closes the store or its sender, so close the store yourself afterwards with `await store.close()`. Several `RunStore` objects over one store each hold their own lease. `from_engine` and `from_database_url` never listen, and nothing warns you: their followers poll. To listen, build the store yourself and wrap it with `RunStore(store)`. A reader whose live updates are unavailable polls instead of failing. If it cannot take its lease, it asks again after 30 seconds; connection failures after that are retried by the transport itself with backoff. The listen URL belongs to the transport: `PostgresUpdates(listen_url=...)`. One `RunStore` shares one lease between all its readers and gives it back after 60 seconds with nothing to watch; see [What a reader does](/docs/guides/scaling#what-a-reader-does). Use one long-lived `RunStore` where you can.

**Shutdown order.** Close the reader before you dispose its engine, in `async with` or a `finally`. One coordinator task per `RunStore` serves every follower, and closing the last follower does not stop it: it ends on its own after about 60 seconds with nothing to watch, or at `close()`. If you dispose the engine first, the coordinator's next read can fail with a pool error (for example a `KeyError`) and log `follow_read_failed`. For a borrowed engine (`RunStore(store)`, `from_engine`), `await reader.close()` and only then `await engine.dispose()`. `async with RunStore.from_engine(engine) as reader:` closes the reader on exit; dispose the engine after the block. A reader from `from_database_url` owns its engine, and `close()` disposes it.

## Tenant scope

Every read takes a keyword-only `tenant_id`, where `TenantScope` is `str | None | UNSCOPED`. The older reads (`list_runs`, `count_runs`, `get_run`, `get_events`, `stream_events`, `get_llm_calls`, `get_tool_invocations`, `get_traces`, `get_pii_mapping`, `get_pauses`, `get_pause_page`, `get_subtree`, `get_notes`, `read_image`) default to `UNSCOPED`. `get_pending`, `follow` and `get_event_view` have **no default**: leaving `tenant_id` out is a `TypeError`.

| Value | Reads |
| --- | --- |
| `"acme"` | that tenant's runs only |
| `None` | untenanted runs only (changed in 0.5.0: `None` used to mean "all" on `list_runs` and `count_runs`) |
| `UNSCOPED` (the default) | every tenant |

A run outside the scope behaves exactly like a missing one, and what "missing" looks like depends on the method:

| Method | Missing or foreign run |
| --- | --- |
| `get_run` | returns `None` |
| `get_events`, `get_llm_calls`, `get_tool_invocations`, `get_traces`, `get_pauses` | return `[]` |
| `get_pause_page` | returns `([], False)` |
| `get_pii_mapping` | returns `{}` |
| `get_notes` | unscoped: returns `[]`; with a `tenant_id`: raises `RunNotFoundError` |
| `get_subtree`, `get_pending`, `follow` (on start), `get_event_view` | raise `RunNotFoundError` |
| `read_image` | raises `BlobNotFoundError`, the same error as for a missing blob |

An empty result is therefore never proof that a run exists. Check `get_run` (or `get_pending`) first when your route needs a 404. The scope is part of the same query as the read. Pass the authenticated caller's tenant from every route of your own; see [Multi-tenancy](/docs/architecture/multi-tenancy).

### Arguments are validated

Every read, `get_pending` and `follow` checks its arguments before it queries, and refuses with a `ValueError` whose message is fixed and never echoes the rejected value. Every such rejection, including the `list_runs` offset cap, the pause-page `limit` and the `stream_events` poll interval, logs `code=read_argument_invalid` with the argument name. A route can map it to HTTP 400.

- Run ids and string tenant ids are non-empty strings of at most 255 characters with no NUL and no unpaired surrogate. `get_run(None)` therefore raises (it used to return `None`).
- Cursors fit a 32-bit integer; `limit` and `offset` are integers (not `bool`). The `list_runs` `offset` is at most 10,000; the `offset` of `get_traces`, `get_llm_calls` and `get_tool_invocations` has no cap (see [Bounded list reads](#bounded-list-reads)).
- `event_types` and `status` hold at most 100 entries.
- `metadata_filter` is a dict of at most 32 keys matching `[A-Za-z0-9_-]{1,128}`, with scalar values (strings up to 4096 characters, finite numbers, `bool` or `None`). Nested values are not supported.
- Date filters (`started_after`, `started_before`, `before`) are timezone-aware `datetime` values.
- Boolean flags (`include_payloads`, `until_terminal`, `active_pause`, `undelivered_only`) must be real `bool` values. A string such as `"false"` raises instead of being read as true.
- `read_image` with a value that is not a SHA-256 hex digest raises `BlobNotFoundError`, like a missing image.

### Pending and live reads

Two calls exist to serve a frontend from your own routes. Both require an explicit `tenant_id` (a string, `None`, or `UNSCOPED`; leaving it out is a `TypeError`) and never fail open. The recipe is [Build your own read routes](/docs/recipes/build-your-own-read-routes).

[//]: # "docs-test: skip - API signature listing, not runnable code"

```python
async def get_pending(run_id: str, *, tenant_id: TenantScope) -> PendingPause | None

def follow(run_id: str, *, tenant_id: TenantScope, after_sequence_index: int | None = None,
           include_payloads: bool = False, until_terminal: bool = True,
           max_duration_s: float | None = 900.0) -> Follow
```

**`get_pending`** returns `None` when the run is not paused and raises `RunNotFoundError` for a missing or foreign run. A `PendingPause` has `run_id`, `status`, `kind` (`client_tool`, `approval`, `input` or `paused`), `pause_id`, `tool_calls` (a list of `PendingToolCall` with `id`, `name`, `target`, `params`, `approval` and `args_hidden`), `question`, `options`, `reason`, `message` and `budget_exceeded`; `to_dict()` gives the `run.paused` event shape plus those fields. It is bounded: the run's history is never loaded, and on Postgres a stored pause is converted to JSON once per read whatever its size. A client-tool or requested pause without pending server calls costs one projected read; an approval, input, or requested pause retaining server calls adds the active-pause sequence and the recorded model arguments, three bounded reads in all. `params` depend on the kind:

| Kind | `params` |
| --- | --- |
| `client_tool` | The arguments the client tool receives. With the default `PII(restore="all")` these hold real values. Authorize the actor before you show them. |
| `approval`, `input` | The arguments exactly as the model sent them (PII placeholders), which is what a person approves. If the recorded model arguments are unavailable, `params` is `None` and `args_hidden` is `True`: resolve that pause on the server, never approve an empty object. |

`get_pending` reports the run you ask about: for a run that delegated, list the tree with `get_subtree` and call `get_pending` for each waiting node.

**`follow`** yields `StoredEvent` items, `FollowHeartbeat` when quiet, and a final `FollowEnd(reason, cursor)` where `reason` is `terminal`, `max_duration`, `lagging` or `error`. Use `async for` (after `await follow.start()` if you want to check the scope and capacity before sending response headers) and `await follow.aclose()` when done. `follow.drained_terminal` is `True` when the run is already finished and has nothing left to send; a route can answer 204 without iterating (see [How a follow ends](#how-a-follow-ends)). One coordinator task per `RunStore` serves every follower in your process and reads the watched runs in batches, so database load grows with watched runs, not with open connections, and one follower costs a small constant number of statements however many pauses the run has. With healthy live updates a hint makes a run due at once and a safety poll runs every 10 seconds; without them an idle run is read every 0.5 seconds, backing off to 2 seconds (see [Scaling](/docs/guides/scaling#what-a-reader-does)). Events pass through the [redacted view](#redacted-views) unless `include_payloads=True`.

Follower limits (`FollowCapacityError`, answer 503 with a short `Retry-After`):

- at most **500 followers per store** (`RunStore.follow` uses one `EventFeed` per store);
- at most **100 per tenant scope** by default, a fifth of the store cap. The cap is per scope, not per user: each string `tenant_id` is one scope, all untenanted (`tenant_id=None`) followers together are one scope, and all `UNSCOPED` followers together are one scope. `FollowCapacityError.per_tenant` tells the two caps apart;
- **900 seconds** per follow by default (`max_duration_s`), ending with a resume cursor.

A single-tenant app that serves more than 100 live readers per process builds its own feed, and calls `feed.follow(...)` instead of `store.follow(...)`:

```python
from dendrux.store import EventFeed

feed = EventFeed(store, max_followers=2000, max_followers_per_tenant=None)
```

`max_followers_per_tenant=None` turns the per-scope cap off; a number sets it. The caps are per process: size them with your worker count and database pool. `EventFeed(batch=...)` is clamped to at most 1,000 events per run in one read, so Dendrux's own reads stay within the page cap; the coordinator may read fewer to share its query budget, and a terminal run is still drained across every page.

**`get_event_view(run_id, event, *, tenant_id, include_payloads=False)`** verifies that the run is in scope. Pass only events read from that same run; `StoredEvent` has no run ID to verify the association. It resolves the active pause and uses the recorded model-sent approval arguments. Prefer it when paging raw `get_events` rows for a UI. Each call costs one status query plus, for a pause event, an active-pause read, so keep pages small and use `follow` for live delivery.

**`redact_event(event, *, include_payloads=False, active_pause=False)`** is a conservative standalone filter with no database context. It cannot prove which names are declared tools, so it shows `<unknown_tool>` for them, and unverified active approval or input arguments are hidden (`params=None`, `args_hidden=True`); never replace them with empty args. All feed and pending types, `EventFeed`, `redact_event` and `RunStore` are importable from `dendrux.store`.

The feed bounds iteration; your HTTP transport must bound blocked sends and call `aclose()` in `finally`, including if no generator iteration begins.

**`EventFeed` arguments.** Pass these to `EventFeed(store, ...)`. `RunStore.follow` uses the defaults.

| Argument | Default | Meaning |
| --- | --- | --- |
| `max_followers` | 500 | Followers in this feed |
| `max_followers_per_tenant` | 100 | Followers per tenant scope; `None` turns the cap off |
| `poll_interval_s`, `poll_max_s` | 0.5, 2.0 | With no healthy live updates, an idle run is read every `poll_interval_s`, doubling up to `poll_max_s`. A new event resets it. Both apply from the first read |
| `poll_healthy_s` | 10.0 | The safety poll while live updates are healthy, with 20 % jitter either way. This is the only place to set it: `RunStore.follow` has no such argument |
| `status_every` | 4 | With no healthy live updates, a status read rides with every Nth events read |
| `batch` | 100 | Most events per run in one read, at most 1,000 |
| `heartbeat_s` | 15.0 | Quiet time before a `FollowHeartbeat` |
| `buffer` | 1,000 | Events held for one follower before it ends as `lagging` |
| `stop_timeout_s` | 5.0 | How long `RunStore.close()` waits for the coordinator |

A run followed through several feeds uses the tightest of their settings.

### How a follow ends

`FollowEnd(reason, cursor)` is the last item. Reconnect with `after_sequence_index=cursor` unless the reason is `terminal`.

| Reason | Meaning |
| --- | --- |
| `terminal` | The run finished and every event was sent. |
| `max_duration` | `max_duration_s` passed. The events still in the buffer are discarded, so reconnect from the last cursor you delivered. |
| `lagging` | This follower fell more than `buffer` events behind. |
| `error` | The reader could not continue. |

**The final event is never lost.** The built-in SQL stores save the terminal status and the terminal event in one transaction, for success, a returned error, the iteration limit, a failure and cancellation, in both storage formats. A follow that sees the terminal status drains the event log, waits 100 ms, and drains once more before it sends `FollowEnd("terminal")`. With an atomic terminal write the last look finds nothing new. A custom store without one gets only that bounded 100 ms grace, which cannot catch an event written arbitrarily late. Custom stores should write status and event together: see [Terminal writes in a custom store](/docs/reference/state-store#terminal-writes-in-a-custom-store).

**Starting on a finished run.** `follow()` first looks for events after your cursor. If there are any, it starts at once, without the 100 ms wait. If there are none, it waits 100 ms and looks once more before it reports `drained_terminal=True`. This keeps the protection against trailing events without delaying a start that already has data to send.

**A lagging follower keeps its slot until you read it.** A follower that ends as `lagging` still holds its tenant and store slot while events remain in its buffer, including the last one in flight. Read the rest of the buffer, or close the follow, to give the slot back. At `max_duration_s` the coordinator drops the buffer and frees the slot and the watch even if you never read again.

### Redacted views

`follow`, `get_event_view`, `redact_event`, `get_pauses` and `get_pause_page` take `include_payloads` (default `False`). With the default, a stored event is shown through a field allowlist: every event type has a rule, and a field survives only if it is one of these:

- a Dendrux enumeration or constant code (a run status, a stop reason, a pause reason, a budget metric, a tool result code);
- a Dendrux-generated id or digest (run, pause and note ids, content hashes);
- a number or a boolean;
- a developer-declared name that Dendrux can prove from configuration (the agent name, skill names, guardrail ids and the tool names the run recorded in its `tools.declared` event, plus Dendrux's own skill tools).

Everything else is hidden or replaced with a placeholder: text written by a model, a provider, a tool, an MCP server, a hook or a client. In practice that means the system prompt, provider requests and responses, tool arguments and results, PII mappings, free text such as a person's answer (`run.resumed.user_input`), a reviewer's denial reason, exception text (`run.error.error`; use `error_info`), image descriptions and a pause's `message`. `error_info` keeps only `category`, `retryable`, `error_type`, a built-in `provider` label, `status_code` and `timeout_reason`; `safe_message`, `model` and `provider_code` are hidden because they can carry vendor text. Tool call ids are hidden too, apart from the active pause's. Placeholders you may see:

| Placeholder | Meaning |
| --- | --- |
| `<unknown_tool>` | A tool name Dendrux cannot prove is a declared tool (a name the model invented, a run with no `tools.declared` record, or `redact_event` without database context). |
| `<mcp_tool>` | A name the run recorded as coming from an MCP server. |
| `<custom_kind>` | A guardrail finding kind that is not one of Dendrux's built-in detectors. |
| `<custom_provider>` | A provider label that is not one of Dendrux's built-in adapters. |
| `<unknown_code>` | A tool result code that is not one Dendrux writes. |
| `<unknown_skill>` | A skill name the model invented. |

**The active pause is the exception.** A client has to act on it, so the arguments, call ids and tool names of the pause the run is waiting on stay visible in `run.paused`, in `get_pending` and in the matching `approval.requested` event. Authorize the actor first: client-tool arguments can hold real personal data. Past pauses are redacted like everything else. `include_payloads=True` is for trusted operators.

**What this protects against.** Redacted readers protect against untrusted *data*: text supplied by models, provider responses, tool results, MCP servers, hook return values and clients. They do not protect against hostile code running in your process. A custom provider, strategy, state store or hook is Python with the full privileges of your server, so it could write any record or read around the redactor, and no library can defend against that. Review that code as you review the rest of your server.

> **Known limit.** A tool name is shown only when the run's `tools.declared` event lists it; that event is written by Dendrux at the start of each run segment from the tools declared in code, never from MCP discovery or model output. Records written by in-process code you control are inside the boundary above. Runs created before 0.5.0 have no such event and show `<unknown_tool>` for tool names outside the active pause.

### Bounded list reads

`get_events`, `get_traces`, `get_llm_calls` and `get_tool_invocations` return lists that grow with the run. Pass `limit=`, a page size from 1 to 1,000, and page through the rest.

- **In 0.6.0, omitting `limit` still requests every matching row and emits a `FutureWarning`.** The warning names the method and the paging argument. In 0.7 the default becomes 1,000 and a `limit` above 1,000 raises.
- **A `limit` above 1,000 also emits a `FutureWarning` and is clamped to 1,000 now.** `SQLStateStore` stores clamp it, and so does the format-2 branch of `get_traces`. A custom store receives the limit unchanged on its format-1 reads and on the event, LLM-call and tool-call reads: `RunStore` warns but does not clamp them. The format-2 public `get_traces` is normalized by `RunStore` whatever the backend, custom checkpointing stores included: an explicit limit is clamped to 1 to 1,000. Internal conversation reconstruction is not given this page clamp.
- **A `limit` of zero or less reads one row** on the SQL stores and the format-2 `get_traces`. (Before this release the format-2 branch returned an empty list.) A custom store receives it unchanged on its format-1 reads.
- Arguments are validated first, then the warning is emitted, before any store call. It uses Python's normal warning filtering and de-duplication. Awaited directly, it points at your line; passed straight to `asyncio.run` or scheduled as a task, it points into asyncio, so await the read from a small wrapper coroutine if you want your own location.
- To find every call that still warns, run your tests or a script with `python -W error::FutureWarning`. `sweep()` raises its own, unrelated `FutureWarning` when it finds stale rows without `on_stale=`.

**How to page.** Keep the tenant scope and every filter identical on each page.

| Method | Page with | Next page |
| --- | --- | --- |
| `get_events` | `after_sequence_index=` (exclusive) | the `sequence_index` of the last event returned |
| `get_traces`, `get_llm_calls`, `get_tool_invocations` | `offset=` | the offset plus the number of rows actually returned |

An empty page ends the walk. A single page is right only when the view intentionally shows just that page. Without a cursor or offset these reads return the first, oldest rows, not the most recent ones: for a run with 1,001 events, `limit=100` returns sequences 0 to 99. There is no reverse-order or latest-page option. A full-history export must loop. The separate reads are best-effort, not one snapshot of a run that is still writing. Process each page as it arrives instead of keeping every row when you can.

```python
    while True:
        page = await reader.get_events(
            run_id, tenant_id=tenant_id, limit=500, after_sequence_index=after
        )
        if not page:
            return events
        events.extend(page)
        after = page[-1].sequence_index
```

**Deep offsets cost more.** An offset page makes the database scan or discard every preceding row, so page 50 costs more than page 1. These reads add no keyset parameter and no offset cap in 0.6.0. For a long history, prefer small numbers of large-enough pages (a few hundred rows) over many tiny ones, and for events use `after_sequence_index`, which the run's event index serves directly.

**Format-2 traces have reconstruction bounds.** For a format-2 run, `get_traces` rebuilds the effective conversation (the latest rewrite prefix expanded, then its suffix) from its stored traces. The default bounds are **20,000 expanded rows** and **16 MiB of UTF-8 JSON**, and both count the rows an `offset` skips. Every page starts reconstruction from the beginning and re-reads what precedes its offset, so repeated paging repeats that work, and a smaller `limit` does not get around either bound. Over a bound, `get_traces` raises `dendrux.errors.RunNotReclaimableError` with `reason="history_too_large"`. `RunStore.get_traces` has no override for these bounds, and a run above them cannot necessarily be read to the end by the loop above. Catch the error and show a clear "history too large" result, labelling any pages you already read as partial; do not retry smaller pages expecting the bound to go away. For complete histories of larger workloads, keep an archive that your own code writes while the run executes, or split the work into smaller runs.

```python
from dendrux.errors import RunNotReclaimableError

try:
    page = await reader.get_traces(run_id, tenant_id=tenant, limit=500, offset=0)
```

### `get_subtree`

A delegated run has child runs, which may have children of their own. `get_subtree` returns the whole tree under a run, with usage rolled up:

[//]: # "docs-test: skip - fragment: relies on `run_id`, defined by setup shown elsewhere"

```python
tree = await store.get_subtree(run_id, max_nodes=10_000)
for node in tree.nodes:                       # breadth-first, root first
    print("  " * node.depth, node.run.run_id, node.run.status, node.usage.known_cost_usd)
print(tree.usage.input_tokens, tree.usage.output_tokens, tree.usage.cost_usd)
```

- `RunSubtree` has `root_run_id`, `nodes` (a `SubtreeNode` each: `run` as a `RunSummary`, `depth` below the root, and that run's own `usage`), `usage` (the sum over every node) and a `root` property.
- `RunUsage` has `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens`, `reasoning_tokens`, `cost_usd`, `known_cost_usd`, `unpriced_calls` and `llm_calls`. `known_cost_usd` is the sum over the priced calls; `cost_usd` equals it only when every call was priced and is `None` when any was not (an unknown cost is never counted as zero).
- **`RunSubtree.usage` is the live rollup of successfully recorded `llm_interactions`.** It includes unfinished runs, but interaction writes are best-effort, so it is not a billing guarantee. The `total_*` fields on each node's `RunSummary` are the snapshots persisted on `agent_runs` and may lag, or read 0 for a run still in progress. Use `usage` for live spend; this is also the figure [budgets](/docs/architecture/budget) enforce.
- The reads are best-effort, not one snapshot transaction. A run that is still writing can make the node list and the usage differ by a call or a child.
- **Tenancy.** Omit `tenant_id` (or pass `UNSCOPED`) for a trusted, unscoped read of all descendants. Pass a string to scope to that tenant, or an explicit `None` to scope to untenanted runs. The root must be in scope (otherwise it reads as missing) and so must every descendant; a run outside the scope is excluded together with everything below it.
- Raises `RunNotFoundError` if the root does not exist or is out of scope.

**Bounding the tree: `max_nodes`.** Pass a positive integer (not `bool`, at most `2**63 - 1`; anything else raises `ValueError` and logs `read_argument_invalid` before any store call). The bound counts descendants only; the run you pass in is not counted, although `tree.nodes` lists it first. The read **refuses when the descendants reach `max_nodes`**: with `max_nodes=10_000`, 9,999 descendants pass (so `tree.nodes` holds up to 10,000 entries, the root included) and 10,000 descendants refuse. Refusal raises `dendrux.errors.SubtreeTooLargeError` (a `ValueError`) carrying `run_id` and `max_nodes`, and logs the code `subtree_limit` with `run_id` and `limit`. Catch it to report the refusal, or retry with a larger bound you chose. The root and every returned descendant stay tenant scoped; foreign-tenant branches are excluded as before.

[//]: # "docs-test: skip - fragment: relies on `store`, `run_id` and `tenant`, defined by setup shown elsewhere"

```python
from dendrux.errors import SubtreeTooLargeError

try:
    tree = await store.get_subtree(run_id, tenant_id=tenant, max_nodes=10_000)
except SubtreeTooLargeError as exc:
    ...  # tell the caller exc.run_id has at least exc.max_nodes descendants
```

This is a **node bound, not a memory bound**: a SQL store can load the root and up to the threshold's worth of descendant rows before it refuses, and the accepted nodes can hold large payloads. A custom store receives `max_nodes` only when its `get_subtree` declares a named parameter that takes a keyword (`**kwargs` alone, positional-only parameters and signatures that cannot be inspected do not qualify). Without it, the store loads its whole tree first and `RunStore` counts the descendants afterwards; a store may also ignore the parameter, so the count is checked after loading in every case.

**In 0.6.0, omitting `max_nodes` (or passing `None`) still reads the whole tree and emits a `FutureWarning`. In 0.7 the default becomes `max_nodes=10_000`.**

### `metadata_filter`

`list_runs` and `count_runs` accept `metadata_filter: dict[str, Any]`. It does exact-match equality across every key in the run's `meta` JSON, AND across keys (`jsonb @>` on Postgres, repeated `json_extract` on SQLite). Keys are restricted to `^[A-Za-z0-9_-]+$`; nested paths are out of scope. The canonical use is per-conversation observability:

```python
runs = await store.list_runs(metadata_filter={"thread_id": "thread_abc"})

```

## Record types

For format-2 runs, `get_traces` returns the effective provider conversation: the expanded latest rewrite prefix followed by its suffix, with state rows and superseded prefixes excluded before counting `offset` or `limit`. PII placeholders remain in this view. The separate `get_pii_mapping` read is for trusted restoration. An expanded prefix entry can share its underlying rewrite row identity with other entries; use the returned conversation position for ordering.

All returned from `dendrux.store`. Fields, exact as persisted:

**`RunSummary`** (from `list_runs`): `run_id`, `agent_name`, `status`, `created_at`, `updated_at`, `iteration_count`, `total_input_tokens`, `total_output_tokens`, `total_cache_read_tokens`, `total_cache_creation_tokens`, `total_cost_usd`, `model`, `parent_run_id`, `delegation_level`, and (0.5.0) `tenant_id`. List views never load pause state, and `offset` is capped at 10,000.

**`RunDetail`** (from `get_run`): every `RunSummary` field plus `strategy`, `input_data`, `answer`, `error`, `failure_reason`, `cancel_requested` (`True` between a `cancel_run` request and the run reaching a terminal status), `pause_requested` (`True` between a `request_pause` request and the run pausing), and (0.5.0) `error_info`, the structured summary of a provider failure that ended the run (`None` otherwise).

**`StoredEvent`** (from `get_events`): `sequence_index`, `iteration_index`, `event_type`, `correlation_id`, `data`, `created_at`.

**`LLMCall`** (from `get_llm_calls`): `iteration`, `provider`, `model`, `input_tokens`, `output_tokens`, `total_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`, `cost_usd`, `duration_ms`, `provider_request`, `provider_response`, `created_at`.

**`ToolInvocation`** (from `get_tool_invocations`): `iteration`, `tool_name`, `tool_call_id`, `provider_tool_call_id`, `target`, `params`, `result`, `success`, `error`, `duration_ms`, `created_at`.

**`TraceEntry`** (from `get_traces`): `role`, `content`, `order_index`, `meta`, `created_at`, `phase` (`"commentary"` for an assistant message that ended in tool calls, `"final_answer"` for the answer turn, `None` for other roles and rows written before phases were recorded).

**`RunSubtree`**, **`SubtreeNode`**, **`RunUsage`** (from `get_subtree`) and **`RunNote`** (from `get_notes`) are described under [`get_subtree`](#get_subtree) and [`get_notes`](#get_notes).

**`PausePair`** (from `get_pauses` and `get_pause_page`): `pause_sequence_index`, `pause_at`, `resume_sequence_index`, `resume_at`, `reason`, `pending_tool_calls`, `submitted_results`, `user_input`, and (0.5.0) `pause_id`. `pending_tool_calls` carries the pending calls' ids, names and parameters, so `get_pauses` is the public way to read a client tool's call ids when you are not holding the original `RunResult` (see [Client-side tools](/docs/recipes/client-tools)). `pause_id` is `None` for pauses recorded before 0.5.0. By default past pauses' arguments, call ids and `user_input` are hidden; pass `include_payloads=True` for a trusted view.

A requested pause that retains server-target or approval-gated calls uses recorded placeholder arguments, or `args_hidden=True` when the current pause has no such evidence. This applies to pending reads and redacted event views, including follow.
